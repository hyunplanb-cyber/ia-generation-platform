골라 읽는 길잡이

언제 필요한가 — 맨 먼저

이 부록은 Claude Code나 Cursor 같은 AI 도구로 화면은 만들었는데, 그다음이 막힌 분을 위해 썼습니다. 개발자가 아니어도 됩니다. 터미널(까만 창)을 처음 봐도 됩니다. 명령어는 전부 통째로 복사할 수 있게 넣었고, 바로 아래에 "이건 무슨 뜻이에요"를 붙였습니다.

순서대로 읽어도 되고, 지금 막힌 곳부터 펴도 됩니다.

  • 남한테 주소를 보내고 싶어요→ 2장. 30분이면 됩니다.
  • 회원가입이 필요한가요?→ 4장. 그전에 5장(데이터 저장)이 먼저 있어야 합니다. 로그인은 결국 "누가 누구인지 어딘가에 적어 두는 일"이라서요.
  • 결제를 받아야 하나요?→ 6장. 다만 3장을 먼저 읽으세요. HTTPS(주소창 자물쇠)가 없으면 결제가 아예 붙지 않습니다. 그리고 6장 맨 앞의 "심사 두 달" 이야기는 지금 당장 읽으세요. 나중에 알면 늦습니다.
  • 새로고침하면 입력한 게 다 사라져요→ 5장.
  • 넣을 사진이 하나도 없어요→ 7장.
  • 사이트 안에서 AI를 쓰고 싶어요→ 8장.
  • 한 군데 고치면 다른 데가 깨져요→ 9장.
  • 내일 문 열어요→ 10장의 체크리스트만 훑으세요.
  • 아무것도 모르겠어요→ 1장부터 그냥 쭉. 중간에 안 쓰는 장은 건너뛰어도 사이트는 뜹니다.

1

내 컴퓨터에서만 보이는 사이트

언제 필요한가 — 만들었는데 나만 보일 때

AI에게 시켜서 화면이 나왔습니다. 그런데 주소창에 localhost:3000이라고 적혀 있고, 친구에게 이 주소를 보내면 아무것도 안 뜹니다. 정상입니다.

localhost가 뭔가요

localhost는 "이 컴퓨터"라는 뜻입니다. 내 컴퓨터 안에서만 통하는 주소예요. 친구가 localhost:3000을 열면 친구의 컴퓨터를 찾아가고, 거기엔 아무것도 없으니 안 뜹니다.

뒤의 3000은 포트 번호입니다. 한 건물(컴퓨터) 안의 방 번호라고 보면 됩니다. 방마다 다른 프로그램이 삽니다.

일단 내 컴퓨터에서 띄우기

AI가 만들어 준 폴더를 터미널(윈도우는 PowerShell, 맥은 터미널)에서 연 다음, 두 줄만 칩니다.

npm install

이건 이런 뜻이에요. "이 사이트가 필요로 하는 부품들을 인터넷에서 받아다 node_modules 폴더에 깔아라." 처음 한 번, 그리고 부품 목록이 바뀔 때만 하면 됩니다. 몇 분 걸리고 글자가 폭포처럼 쏟아지는 게 정상입니다.

npm run dev

이건 이런 뜻이에요. "개발용으로 사이트를 켜라." 켜 두면 코드를 고칠 때마다 브라우저가 알아서 새로 그려 줍니다. 끄려면 그 창에서 Ctrl+C.

잘 되면 이렇게 나옵니다.

  ▲ Next.js 16.2.10
  - Local:        http://localhost:3000
  ✓ Ready in 2.1s
이 오류가 뜨면

npm : 'npm' 용어가 cmdlet ... 인식되지 않습니다 / command not found: npm
Node.js가 안 깔려 있습니다. nodejs.org에서 LTS 버전을 받아 설치하고, 터미널을 완전히 껐다 다시 켜세요. 껐다 켜지 않으면 설치했는데도 똑같은 소리를 합니다.

Port 3000 is in use
3000번 방에 이미 다른 게 살고 있습니다. 대개 Next.js가 알아서 3001로 옮겨 줍니다. 주소창의 숫자를 그대로 따라가면 됩니다.

화면은 뜨는데 글자만 잔뜩 있고 디자인이 없다
npm install이 끝나기 전에 열었을 가능성이 큽니다. 터미널에서 설치가 끝난 걸 확인하고 새로고침하세요.

비밀 쪽지 — .env.local

사이트가 커지면 "코드에 적으면 안 되는 값"이 생깁니다. 데이터베이스 주소, 로그인 열쇠, AI 사용 키 같은 것들이요. 이걸 환경변수(프로그램에 몰래 넘기는 비밀 쪽지)라고 부르고, 보통 프로젝트 맨 위에 .env.local이라는 파일을 만들어 한 줄에 하나씩 적습니다.

# .env.local — 이름=값 형식. 따옴표 없이.
DATABASE_URL=postgresql://...
BETTER_AUTH_SECRET=아주_길고_아무도_모르는_문자열
ANTHROPIC_API_KEY=sk-ant-...

이건 이런 뜻이에요. "이 값들을 프로그램이 실행될 때 몰래 손에 쥐여 줘라." 파일 이름 앞의 점(.)을 빼먹으면 안 됩니다. 값을 고쳤으면 npm run dev를 껐다 켜야 반영됩니다.

같이 두는 게 .env.example입니다. 여기엔 값을 비운 채 이름만 적습니다. 나중에 다른 사람이(또는 반년 뒤의 내가) "뭘 채워야 하지?"를 알 수 있게요. 우리 사이트의 .env.example은 이렇게 생겼습니다.

# Neon Postgres 연결 문자열 (Neon 대시보드 → Connect에서 복사)
DATABASE_URL=

# Better Auth
BETTER_AUTH_SECRET=
BETTER_AUTH_URL=http://localhost:3000

# 소셜 로그인 (설정하지 않으면 해당 버튼은 자동으로 숨겨짐)
GOOGLE_CLIENT_ID=
GOOGLE_CLIENT_SECRET=

절대 올리면 안 되는 것

비밀 쪽지가 온라인 창고(깃허브)에 그대로 올라가면 큰일 납니다. 그래서 .gitignore라는 파일에 "얘네는 창고에 넣지 마"라고 적어 둡니다.

# .gitignore
.env*
!.env.example
node_modules
.next
client_secret_*.json

이건 이런 뜻이에요. ".env로 시작하는 파일은 전부 무시해라. 단 .env.example만은 예외로 올려라(!가 예외 표시). 부품 폴더와 빌드 찌꺼기도 무시해라."

우리가 겪은 것

구글이 던져 준 파일이 폴더에 굴러다닙니다

소셜 로그인을 붙이려고 구글 클라우드 콘솔에서 설정을 마치면, client_secret_960122....apps.googleusercontent.com.json 같은 파일이 자동으로 다운로드됩니다. 이걸 프로젝트 폴더에 그대로 두면, 아무 생각 없이 git add . 한 번에 구글 로그인 열쇠가 통째로 인터넷에 공개됩니다.

그래서 우리는 .gitignore에 아예 못을 박아 뒀습니다.

# 구글 OAuth 클라이언트 시크릿 파일 — 절대 커밋되면 안 됨
client_secret_*.json

지금 바로 하세요. 다음 장에서 깃허브에 올리기 전에, 프로젝트 폴더에 client_secret이나 .pem, .key로 끝나는 파일이 없는지 한 번 훑어보고 .gitignore에 넣으세요. 한 번 올라간 비밀은 지워도 기록에 남습니다.

2

세상에 올리기 (Vercel)

언제 필요한가 — 남에게 주소를 보내고 싶을 때

여기가 이 부록의 첫 고비이자, 사실 제일 쉬운 곳입니다. 순서는 이렇습니다.

내 컴퓨터 → 깃허브(창고) → Vercel(서버)

Vercel은 깃허브 창고를 쳐다보고 있다가, 새 코드가 올라오면 알아서 사이트를 다시 지어 올립니다. 그래서 한 번 연결해 두면 그다음부터는 "고치고 → 올리고 → 끝"입니다.

1) 깃허브에 창고 만들기

github.com에 가입하고, 오른쪽 위 + → New repository를 누릅니다. 이름은 아무거나(예: my-site), Private(비공개)로 두세요. 나머지 체크박스는 전부 건드리지 않는 게 편합니다.

📷 캡처 필요 GitHub의 New repository 화면. 이름 입력칸과 Private 선택이 보이게, 다른 옵션은 체크 안 된 상태로.

2) 내 폴더를 창고에 올리기

프로젝트 폴더에서 터미널을 열고 아래를 차례로 칩니다. 마지막 줄의 주소는 방금 만든 창고 주소로 바꾸세요.

git init
git add .
git commit -m "첫 커밋"
git branch -M main
git remote add origin https://github.com/내계정/my-site.git
git push -u origin main

한 줄씩 이런 뜻이에요.
git init — 이 폴더에 "변경 기록장"을 만들어라.
git add . — 이 폴더의 모든 파일을 기록 대상에 올려라. (.gitignore에 적은 건 알아서 빠집니다.)
git commit -m "첫 커밋" — 지금 상태를 "첫 커밋"이라는 이름으로 저장해라.
git branch -M main — 기본 줄기 이름을 main으로 해라.
git remote add origin ... — 온라인 창고 주소를 origin이라는 별명으로 등록해라.
git push -u origin main — 저장한 걸 그 창고로 올려라.

이 오류가 뜨면

Author identity unknown / Please tell me who you are
이름과 메일을 한 번만 등록하면 됩니다.

git config --global user.name "내이름"
git config --global user.email "내메일@example.com"

비밀번호를 물어보는데 넣어도 계속 틀렸다고 함
깃허브는 더 이상 계정 비밀번호를 받지 않습니다. 브라우저 로그인 창이 뜨면 그걸로 하시고, 안 뜨면 GitHub CLI를 깔아 gh auth login 한 번이 제일 빠릅니다.

올리고 나서 .env.local이 창고에 보인다
.gitignore를 나중에 만들었을 때 생깁니다. 그 파일에 든 키를 전부 새로 발급받아 갈아 끼우세요. 지우는 걸로는 부족합니다 — 기록에 남아 있습니다.

3) Vercel에 연결하기

  1. vercel.com에 깃허브 계정으로 가입합니다. (따로 가입하면 창고를 못 봅니다.)
  2. Add New → Project를 누릅니다.
  3. 방금 만든 창고를 고르고 Import.
  4. Next.js 프로젝트면 설정은 건드릴 게 없습니다. 그대로 Deploy.
📷 캡처 필요 Vercel의 Import Git Repository 화면. 내 깃허브 저장소 목록과 Import 버튼이 보이게.

1~3분 뒤 내프로젝트이름.vercel.app 같은 주소가 나옵니다. 이 주소는 이제 누구에게나 보입니다. 친구에게 보내 보세요.

4) 비밀 쪽지를 Vercel에도 넣기 — 여기서 제일 많이 막힙니다

.env.local은 깃허브에 올라가지 않습니다. (1장에서 일부러 막았죠.) 그래서 Vercel은 그 값을 모릅니다. 직접 넣어 줘야 합니다.

Vercel 프로젝트 → Settings → Environment Variables에서 .env.local에 적은 이름과 값을 하나씩 넣습니다. (여러 줄을 한 번에 붙여넣는 것도 됩니다.)

📷 캡처 필요 Vercel Settings → Environment Variables 화면. Key/Value 입력칸과 Production/Preview/Development 선택이 보이게.
놓치기 쉬운 것

환경변수를 넣은 뒤에는 다시 배포해야 반영됩니다. 이미 지어진 사이트는 옛 값을 들고 있습니다. Deployments 탭에서 맨 위 배포의 ⋯ → Redeploy를 누르세요.

NEXT_PUBLIC_으로 시작하는 이름은 브라우저에 그대로 노출됩니다. 비밀 키에는 절대 이 접두사를 붙이지 마세요. 반대로 결제창 클라이언트 키처럼 원래 공개해도 되는 값은 이 접두사가 있어야 화면 쪽에서 쓸 수 있습니다.

우리가 겪은 것

"내 컴퓨터에선 되는데 Vercel에선 안 돼요"의 3대 범인

① 환경변수를 안 넣었다. 대부분 이겁니다. 빌드는 성공했는데 열면 500 오류가 납니다.

② 파일 이름 대소문자. 윈도우와 맥은 Header.tsx와 header.tsx를 같은 파일로 봅니다. Vercel이 도는 리눅스는 다른 파일로 봅니다. 그래서 내 컴퓨터에선 멀쩡한데 Vercel에서만 "그런 파일 없다"고 합니다.

③ 코드가 아닌 파일은 배포에 안 실린다. 우리는 손님이 내려받을 zip 파일들을 packs/ 폴더에 두는데, 이건 코드가 아니라 데이터라서 Vercel이 "안 쓰는 파일"로 보고 빼 버렸습니다. 내 컴퓨터에선 다운로드가 되는데 실서버에서만 파일을 못 찾았죠. 다운로드 경로에만 그 폴더를 같이 실어 보내도록 못 박아서 풀었습니다.

// next.config.ts
outputFileTracingIncludes: {
  "/api/packages/[packageId]/[planId]/download": ["./packs/**/*"],
}

엑셀·PDF·zip처럼 코드가 직접 import 하지 않는 파일을 쓰신다면 같은 일이 생깁니다.

그다음부터는 이 세 줄이 전부입니다

git add .
git commit -m "무엇을 고쳤는지 한 줄"
git push

이건 이런 뜻이에요. "고친 걸 전부 담아 → 이름표를 붙여 저장하고 → 창고로 올려라." 올리는 순간 Vercel이 알아서 다시 짓습니다. 1~2분 뒤 실제 사이트가 바뀝니다.

요금. Vercel에는 개인이 쓸 수 있는 무료 범위가 있고, 우리도 그 안에서 시작했습니다. 다만 무료 범위의 조건(트래픽·함수 실행 시간·상업적 사용 가능 여부 등)은 자주 바뀌므로, vercel.com의 요금 안내를 직접 확인하세요. 이 문서에 숫자를 적어 두면 그게 곧 거짓말이 됩니다.
3

내 도메인 붙이기 + 자물쇠(HTTPS)

언제 필요한가 — .vercel.app 말고 내 주소를 쓰고 싶을 때

my-site-8fk2.vercel.app은 명함에 못 적습니다. 그리고 결제를 받으려면 내 도메인이 사실상 필수입니다(6장). 이 장은 30분이면 끝나지만, 마지막에 반나절 기다리는 구간이 있습니다.

1) 이름 사기

도메인은 사는 게 아니라 매년 빌리는 겁니다. 파는 곳(등록대행사)은 여러 곳입니다.

  • 가비아, 후이즈 등 국내 업체 — 한국어 고객센터, 세금계산서 발행이 편합니다.
  • Cloudflare Registrar, Namecheap 등 해외 업체 — 대개 더 쌉니다.
  • Vercel Domains — Vercel 안에서 바로 살 수 있어 설정이 제일 간단합니다.

가격은 .com이냐 .kr이냐, 어디서 사느냐에 따라 다르고 자주 바뀝니다. 사기 전에 그 사이트에서 직접 확인하세요. 특히 "첫해 할인가"와 "갱신가"가 다른 경우가 많으니 갱신가를 보세요.

2) Vercel에 붙이기

Vercel 프로젝트 → Settings → Domains → 산 주소를 입력하고 Add.

그러면 Vercel이 "당신의 도메인 관리 화면에 이 값을 넣으세요"라고 알려 줍니다. 보통 둘 중 하나입니다.

넣을 곳종류이름값
도메인 산 곳의 DNS 관리A@ (또는 비움)Vercel이 알려 주는 IP
도메인 산 곳의 DNS 관리CNAMEwwwVercel이 알려 주는 주소

이게 무슨 일이냐면. DNS는 "이 이름으로 찾아오면 저 서버로 보내 주세요"라고 적어 두는 전화번호부입니다. 그 전화번호부에 Vercel 주소를 적어 넣는 것뿐입니다.

📷 캡처 필요 Vercel Settings → Domains 화면. 도메인이 추가되고 "Invalid Configuration" 또는 체크 표시가 뜬 상태와, 아래에 넣어야 할 A/CNAME 레코드 값이 보이게.
이 오류가 뜨면

Invalid Configuration
거의 항상 ① 값을 잘못 넣었거나 ② 아직 퍼지지 않은 것입니다. DNS는 전 세계에 반영되는 데 보통 몇 분~몇 시간, 길면 하루가 걸립니다. 값을 다시 한 번 대조하고, 맞다면 커피 한 잔 마시고 새로고침하세요.

기존에 있던 레코드와 충돌한다고 함
도메인을 사면 업체가 자기네 안내 페이지로 가는 레코드를 미리 넣어 둡니다. 그 @와 www 레코드를 지우고 Vercel 값으로 갈아 끼우세요.

3) 자물쇠(HTTPS)는 저절로 붙습니다

주소창의 자물쇠 = HTTPS = 나와 서버 사이의 대화를 남이 못 엿보게 암호로 감싸는 것입니다. 예전엔 인증서를 사서 서버에 설치하는 성가신 일이었지만, Vercel은 도메인 연결이 확인되면 무료로 알아서 발급하고 자동으로 갱신합니다. 할 일이 없습니다.

다만 DNS가 다 퍼지기 전까지는 "안전하지 않음"이라고 뜰 수 있습니다. 잠시 기다리면 됩니다.

4) apex냐 www냐 — 지금 정하세요

caffeinecolor.com(apex, 점 없는 맨 앞) 과 www.caffeinecolor.com은 기술적으로 다른 주소입니다. 둘 다 등록하되 어느 쪽을 대표로 쓸지 정하고, 나머지는 그쪽으로 넘겨주게(리다이렉트) 설정하세요. Vercel Domains 화면에서 고를 수 있습니다.

우리가 겪은 것

로그아웃 버튼이 안 눌리는데 오류도 안 뜹니다

도메인을 붙인 뒤, 로그인은 잘 되는데 로그아웃만 안 됐습니다. 화면엔 아무 말도 없고, 개발자 도구를 열어야 403이 보였습니다.

원인은 이랬습니다. 로그인 라이브러리는 보안을 위해 "신뢰하는 주소 목록"을 두고, 상태를 바꾸는 요청(로그아웃 같은)이 그 목록에 없는 주소에서 오면 거부합니다. 우리는 목록에 https://caffeinecolor.com만 적어 뒀는데, 실제 서비스는 www가 붙은 주소로 돌고 있었습니다. 그래서 "모르는 곳에서 온 요청"으로 튕긴 겁니다.

지금은 주소 하나만 적어 두면 apex와 www 두 형태가 함께 따라오도록 계산해서 넣습니다.

// lib/auth.ts — 두 형태를 모두 신뢰 출처에 넣는다
function productionOrigins() {
  const site = process.env.NEXT_PUBLIC_SITE_URL ?? "https://caffeinecolor.com";
  const host = new URL(site).host.replace(/^www\./, "");
  return [`https://${host}`, `https://www.${host}`];
}

교훈. 도메인을 붙이고 나면 로그인만 확인하고 끝내지 마세요. 로그아웃, 글쓰기, 결제처럼 "누르면 서버 상태가 바뀌는" 동작을 한 번씩 눌러 보세요. 조용히 실패하는 것들이 여기 숨어 있습니다.

4

회원가입 · 로그인 붙이기

언제 필요한가 — 사람마다 다른 걸 보여줘야 할 때

먼저 읽으세요

로그인은 "누가 가입했는지 어딘가에 적어 두는 일"입니다. 적어 둘 곳, 즉 데이터베이스가 먼저 있어야 합니다. 5장을 먼저 하고 오시는 게 순서상 맞습니다. (이미 있다면 그냥 진행하세요.)

비밀번호를 직접 다루지 마세요

회원가입 폼을 만들고 비밀번호를 받는 순간, 당신은 남의 비밀번호를 보관하는 사람이 됩니다. 제대로 하려면 암호화·재설정 메일·유출 대응·무차별 대입 방어까지 전부 필요합니다. 1인 사업자가 감당할 일이 아닙니다.

우리가 고른 길: 비밀번호를 아예 안 받습니다. 구글·네이버·카카오 로그인만 씁니다. 그러면 우리 DB에 비밀번호가 한 줄도 없습니다. 유출될 것 자체가 없죠.

// lib/auth.ts
// 이메일·비밀번호는 가입도 로그인도 받지 않는다 — 비밀번호를 아예 보관하지 않기 위해서.
// 화면에서 폼을 지우는 것만으로는 API 직접 호출을 막지 못하므로 서버에서도 잠근다.
emailAndPassword: { enabled: false },

주석의 뒷문장이 핵심이에요. 화면에서 입력칸을 지워도, 서버 주소를 아는 사람은 직접 요청을 보낼 수 있습니다. 막을 거면 서버에서 막아야 진짜로 막힌 겁니다. 이건 로그인만이 아니라 모든 기능에 해당합니다.

붙이는 순서

  1. 라이브러리를 고릅니다. 우리는 Better Auth를 씁니다. Next.js와 잘 맞고, 데이터를 우리 DB에 그대로 넣어 줍니다. (다른 선택지도 많습니다.)
  2. 비밀 열쇠를 만듭니다. 세션(로그인 상태)을 서명하는 데 쓰는 긴 문자열입니다.
npx better-auth secret

이건 이런 뜻이에요. "아무도 못 맞힐 긴 임의 문자열을 하나 만들어 줘." 나온 값을 .env.local의 BETTER_AUTH_SECRET= 뒤에 붙입니다. 이 명령이 안 되면 아무 비밀번호 생성기로 40자 이상 만들어도 됩니다. 이 값이 바뀌면 로그인한 사람들이 전부 로그아웃됩니다. 한 번 정하고 건드리지 마세요.

  1. 소셜 로그인 앱을 등록합니다. 각 회사 개발자 콘솔에서 앱을 만들고 클라이언트 ID와 시크릿 두 개를 받습니다.
    • 구글 — Google Cloud Console → API 및 서비스 → 사용자 인증 정보
    • 네이버 — 네이버 개발자 센터
    • 카카오 — 카카오 디벨로퍼스
  2. 돌아올 주소(리다이렉트 URI)를 등록합니다. 여기가 제일 자주 틀립니다.
이 오류가 뜨면

redirect_uri_mismatch / "등록되지 않은 Callback URL"
구글 로그인 붙일 때 열에 아홉은 이 오류를 봅니다. 사용자가 로그인을 마치면 소셜 회사가 다시 우리 사이트로 돌려보내는데, 그 돌아올 주소를 미리 등록해 두지 않으면 거부합니다.

내 컴퓨터용과 실서버용, 둘 다 등록해야 합니다.

http://localhost:3000/api/auth/callback/google
https://내도메인.com/api/auth/callback/google

글자 하나, 슬래시 하나까지 똑같아야 합니다. http/https도 구분합니다. 3장에서 www를 대표로 쓰기로 했다면 www가 붙은 주소로 등록하세요.

우리가 겪은 것

키가 없으면 버튼이 저절로 사라지게 만들어 뒀습니다

소셜 로그인은 보통 한꺼번에 붙이지 못합니다. 구글은 오늘 되고, 네이버는 심사가 남았고, 카카오는 다음 주에 하고… 그동안 눌러도 아무 일 없는 버튼이 로그인 화면에 남아 있으면, 손님은 "고장 난 사이트"라고 판단하고 나갑니다.

그래서 키가 들어 있는 소셜만 켜지고, 없으면 버튼 자체가 화면에서 사라지게 만들었습니다.

// lib/social-providers.ts — 키가 다 있는 것만 true
export function getEnabledSocialProviders() {
  return {
    google: !!(process.env.GOOGLE_CLIENT_ID && process.env.GOOGLE_CLIENT_SECRET),
    naver:  !!(process.env.NAVER_CLIENT_ID  && process.env.NAVER_CLIENT_SECRET),
    kakao:  !!(process.env.KAKAO_CLIENT_ID  && process.env.KAKAO_CLIENT_SECRET),
  };
}

서버 쪽 설정도 같은 조건으로 짜서, 환경변수를 넣는 것만으로 그 소셜이 켜지고 화면에도 버튼이 나타납니다. 코드를 다시 고칠 일이 없습니다.

이 발상은 로그인 밖에서도 그대로 씁니다. "아직 안 되는 것은 화면에서 지운다." 6장의 결제 스위치도 같은 생각입니다.

알아 두면 편한 것

포트가 매번 바뀌어서 로그인이 깨진다면. 다른 프로젝트가 3000번을 쓰고 있으면 3001, 3002로 뜹니다. 그때마다 리다이렉트 URI를 다시 등록할 순 없으니, 우리는 개발 중에는 localhost의 모든 포트를 신뢰하도록 열어 뒀습니다. 실서버는 3장에서 계산한 실제 도메인만 신뢰합니다.

trustedOrigins: ["http://localhost:*", ...productionOrigins()],
📷 캡처 필요 구글 클라우드 콘솔의 "승인된 리디렉션 URI" 입력 화면. localhost와 실제 도메인 두 줄이 함께 들어간 상태.
5

데이터 저장하기 (Neon)

언제 필요한가 — 새로고침하면 입력한 게 다 사라질 때

AI가 만들어 준 화면은 대개 데이터를 메모리에 들고 있습니다. 새로고침하면 그 메모리가 비워지니 전부 사라집니다. 남기려면 데이터베이스에 적어야 합니다.

Neon이 뭔가요

PostgreSQL(줄여서 Postgres)이라는 데이터베이스를 내가 서버를 관리하지 않고 쓰게 해 주는 서비스입니다. 가입하고 몇 번 누르면 "연결 문자열" 하나가 나오고, 그걸 환경변수에 넣으면 끝입니다.

우리가 Neon을 고른 이유는 Vercel 같은 곳과 궁합이 좋아서입니다. 자세한 이유는 뒤의 "우리가 겪은 것"에서 설명합니다.

1) 연결 문자열 받기

  1. neon.tech에 가입 → 프로젝트 생성. 지역(Region)은 손님이 있는 곳과 가까운 데로 고르세요. 한국이면 ap-southeast-1(싱가포르)처럼 아시아 쪽이 낫습니다.
  2. 대시보드의 Connect 버튼 → 연결 문자열 복사.
  3. .env.local에 붙입니다.
DATABASE_URL=postgresql://사용자:비밀번호@ep-xxxx.aws.neon.tech/neondb?sslmode=require

이 한 줄을 풀면. "이 사용자와 비밀번호로, 저 주소의 neondb라는 데이터베이스에, 암호화된 연결로(sslmode=require) 접속해라." 맨 뒤 ?sslmode=require를 실수로 지우면 접속이 거부됩니다.

📷 캡처 필요 Neon 대시보드의 Connect 화면. 연결 문자열과 복사 버튼이 보이게(비밀번호 부분은 가려서).

Vercel에도 같은 값을 넣으세요. (2장 4번을 잊지 마세요. 안 넣으면 배포된 사이트만 500 오류가 납니다.)

2) 표를 만들고, 바꾼 걸 기록으로 남기기

데이터베이스는 결국 표입니다. "회원 표", "주문 표"처럼요. 그 표의 모양을 코드로 적어 두고(스키마), 그걸 실제 데이터베이스에 반영하는 게 마이그레이션입니다.

우리는 Drizzle이라는 도구를 씁니다. 표 모양은 db/schema.ts에 적고, 두 줄을 칩니다.

npx drizzle-kit generate

이건 이런 뜻이에요. "내가 적은 표 모양과 지금 데이터베이스를 비교해서, 차이만큼의 명령서를 파일로 만들어 줘." drizzle/ 폴더에 0000_...sql 같은 파일이 생깁니다.

npx drizzle-kit migrate

이건 이런 뜻이에요. "그 명령서를 실제 데이터베이스에 실행해라." 이제 진짜 표가 만들어집니다.

표를 고칠 때마다 이 두 줄을 반복하면, drizzle/ 폴더에 변경 기록이 번호순으로 쌓입니다. 우리 프로젝트엔 지금 0000부터 0013까지 열네 개가 쌓여 있습니다. 이 폴더를 지우지 마세요. "지금까지 무엇을 어떻게 바꿨는지"의 유일한 기록입니다.

배포한 사이트만 500 Internal Server Error
거의 DATABASE_URL이 Vercel에 없는 겁니다. 데이터베이스 주소는 빌드할 땐 없어도 통과하고, 실제로 접속할 때 터집니다. 그래서 "빌드는 성공했는데 열면 오류"라는 헷갈리는 모양이 됩니다.

too many connections

우리가 겪은 것

서버리스에서는 "평범한 DB 연결"이 오히려 사고를 냅니다

Vercel 같은 곳은 요청이 올 때마다 아주 작은 서버를 잠깐 켰다 끄는 방식으로 돕니다(서버리스). 문제는 데이터베이스 연결이에요. 보통의 방식은 "연결을 하나 맺어 두고 계속 재사용"하는 건데, 매번 켰다 꺼지는 환경에서는 재사용이 안 되고 연결만 계속 새로 쌓입니다. 손님이 몰리면 too many connections로 사이트가 멈춥니다.

그래서 우리는 Neon이 주는 서버리스 전용 드라이버를 씁니다. 연결을 붙들고 있는 대신 HTTP로 질문하고 답을 받는 방식이라, 켰다 꺼지는 환경에서 안전합니다. 코드는 이 두 줄이 전부입니다.

// db/client.ts
const sql = neon(process.env.DATABASE_URL!);
export const db = drizzle({ client: sql, schema });

알아 두실 것. "Postgres 쓰는 법" 튜토리얼을 그대로 따라 하면 대개 일반 드라이버(pg)를 쓰라고 합니다. 내 컴퓨터에선 잘 되고, 배포하면 사람이 몰릴 때만 터집니다. 제일 나쁜 종류의 버그죠. 서버리스에 올릴 거면 처음부터 서버리스용 드라이버로 시작하세요.

백업. Neon에는 과거 시점으로 되돌리는 기능과, 데이터베이스를 통째로 복제해 실험용으로 쓰는 브랜치 기능이 있습니다. 표 구조를 크게 바꾸기 전엔 브랜치를 하나 떠 놓고 거기서 먼저 해 보세요. 보관 기간·개수 같은 조건은 요금제마다 다르니 Neon 사이트에서 직접 확인하세요.

결제 받기 (토스) + 심사 두 달의 진실

언제 필요한가 — 돈을 받아야 할 때

먼저 읽으세요

3장(도메인 + HTTPS)을 먼저 끝내세요. PG 심사는 실제로 도는 사이트 주소를 보고 합니다. .vercel.app 임시 주소나 자물쇠 없는 사이트로는 시작조차 못 합니다.

우리가 겪은 것

PG 심사는 1~2달 걸립니다. 이걸 모르고 두 달을 날렸습니다

우리는 "사업자등록증만 있으면 결제는 며칠이면 붙는다"고 생각했습니다. 아니었습니다.

카드 결제를 받으려면 PG사(토스페이먼츠 등)와 계약해야 하고, 그 전에 심사가 있습니다. 서류를 내고, 보완 요청을 받고, 다시 내고, 카드사 쪽 확인을 기다립니다. 우리 경우 두 달이 걸렸습니다. 업종과 서류 상태에 따라 더 짧을 수도, 더 길 수도 있습니다.

더 나쁜 건 순서가 있다는 겁니다. 심사를 넣으려면 그 앞에 통신판매업 신고가 되어 있어야 하고, 통신판매업 신고를 하려면 사업자등록이 있어야 합니다. 이 셋은 동시에 못 하고 줄줄이 걸립니다. 우리는 통신판매업 신고를 2026년 7월 27일에 마쳤고, 그제서야 전자상거래법상 표시해야 할 항목이 다 갖춰졌습니다.

// 표시 항목은 흩어 두지 말고 한곳에서 관리하세요.
// 푸터·문의·약관·개인정보처리방침이 전부 여기를 봅니다.
export const BUSINESS = {
  name: "카페인컬러",
  ceo: "최현",
  registrationNo: "608-79-25359",
  mailOrderNo: "제 2026-서울강남-04184 호",  // 통신판매업 신고번호
  address: "서울특별시 강남구 ...",
  email: "...", phone: "...",
};

지금 결제를 붙일 생각이 조금이라도 있다면, 다른 걸 만들기 전에 서류부터 넣으세요. 기다리는 두 달 동안 코드는 얼마든지 만들 수 있지만, 서류는 기다리는 것 말고 할 수 있는 게 없습니다.

기다리는 동안 하면 안 되는 것 — 살 수 없는 값을 보여주는 일

여기가 진짜 함정입니다. 사이트는 다 만들었고, 가격표도 예쁘게 나왔습니다. 그런데 결제가 안 붙었습니다.

이때 가격표를 그냥 띄워 두면 어떻게 될까요.

  • 손님이 값을 봅니다. "89,000원이구나."
  • 사려고 버튼을 누릅니다. 아무 일도 안 일어나거나, "준비 중입니다"가 뜹니다.
  • 손님은 값만 기억하고 나갑니다. 우리는 지키지 못할 약속을 한 셈이 됩니다.

그래서 우리는 스위치를 만들었습니다. 뒤쪽(주문 만들기 → 결제 → 다운로드)은 전부 다 만들어 두고, 화면에서만 막습니다. 승인이 나면 값 하나를 true로 바꾸는 것만으로 판매가 열립니다.

// lib/flags.ts — 아직 열지 않은 기능의 스위치

/**
 * AI팩을 우리 사이트에서 직접 살 수 있게 하는가.
 *
 * "구매하기 → 결제 → 바로 다운로드"까지 뒤쪽은 다 만들어 두고, 화면에서만 막는다.
 * PG 승인이 1~2달 걸리는 동안 버튼을 열어두면 살 수 없는 값만 보이기 때문이다.
 * 승인이 나면 이 값을 true로 바꾸는 것만으로 판매가 열린다.
 */
export const PACKAGE_SALE_OPEN = process.env.PACKAGE_SALE_OPEN === "true";

/**
 * AI팩 판매가를 손님에게 보여주는가.
 * 값만 보이고 살 수 없으면 "비싸다"는 인상만 남고 돌아가기 때문이다.
 */
export const PACKAGE_PRICES_PUBLIC = false;

이 방식의 좋은 점. process.env....=== "true" 로 써 두면 코드를 안 고치고 Vercel 환경변수만 바꿔서 켤 수 있습니다. 잘못되면 다시 끄면 되고요. 값이 false인 동안 화면은 값 대신 상태를 적습니다 — 우리는 "판매 준비 중"이라고 씁니다.

스위치를 만들 때의 요령

왜 껐는지를 주석에 적으세요. 반년 뒤에 이 false를 보면 "이거 왜 꺼져 있지? 켜도 되나?"가 됩니다. 우리 flags.ts는 스위치마다 문단짜리 설명이 붙어 있고, 그게 코드보다 훨씬 값집니다.

화면만 막지 말고 서버도 막으세요. 우리는 충전 페이지에 직접 주소로 들어와도 대시보드로 돌려보냅니다. 버튼만 숨기면 주소를 아는 사람은 그냥 들어갑니다.

우리가 겪은 것

무료 체험 기간을 3일로 뒀다가, 90일로 늘렸습니다

처음엔 가입하면 무료 크레딧을 주고 3일 안에 쓰게 했습니다. "빨리 써 보고 결제하세요"라는 흔한 설계죠.

그런데 결제 자체가 막혀 있었습니다. 누를 대상이 없는 압박이었던 겁니다. 그리고 더 큰 문제가 있었습니다 — PG 심사가 두 달인데 체험이 3일이면, 지금 가입한 사람은 문 여는 날 이미 크레딧이 사라져 있습니다. 유튜브·인스타를 보고 찾아와 준 사람들을 불러 놓고 아무것도 못 하게 만드는 셈이었죠.

3일 → 30일 → 90일로 두 번 늘렸습니다. 30일도 부족했거든요. 심사가 두 달인데 30일이면 결과는 똑같습니다.

// lib/credits.ts
// 유효기간이 90일인 이유: 결제(PG)가 붙기 전까지의 한시 설정이다.
// 30일로 뒀다가 90일로 늘린 이유: PG 승인이 1~2달 걸린다. 30일이면 지금 가입한
// 사람은 문 여는 날 이미 크레딧이 소멸해 있고, 불러 놓고 아무것도 못 하게 된다.
// PG를 열 때 3일로 되돌릴 것. 약관의 표기도 함께 고쳐야 한다.
export const FREE_CREDITS = 35;
export const FREE_TTL_DAYS = 90;

같이 챙길 것 두 가지. ① 되돌릴 때 약관에 적어 둔 기간도 같이 고쳐야 합니다. 코드만 고치면 약관이 거짓말이 됩니다. ② 안내 문구도 상태를 따라가야 합니다. 충전이 안 열렸는데 "충전하세요"라고 하면 손님은 갈 곳이 없습니다.

return creditsOpen
  ? "크레딧이 부족해요. 충전한 뒤 다시 시도해 주세요."
  : "무료 크레딧을 다 쓰셨어요. 충전 기능을 준비하고 있어요.";

테스트 키로는 지금 당장 전부 만들 수 있습니다

심사를 기다리며 손 놓고 있을 필요가 없습니다. 토스페이먼츠는 가입만 하면 테스트 키를 바로 줍니다. 테스트 키로 결제창을 띄우고, 카드번호를 넣고, 성공 화면까지 실제와 똑같이 동작시켜 볼 수 있습니다. 돈만 안 빠져나갑니다.

우리도 그렇게 했습니다. 결제 연동을 다 붙여 놓고, 스위치는 닫아 두고, 환경변수로만 켜서 테스트했습니다.

// 결제 연동은 붙였지만, 검증 전까지 기본은 닫아둔다.
// 환경변수 CREDITS_OPEN=true 로 켜서 테스트하고, 준비되면 유지한다.
// (테스트 키가 들어간 상태라, 켜도 실제 결제는 되지 않고 테스트 모드로만 동작한다.)
export const CREDITS_OPEN = process.env.CREDITS_OPEN === "true";

결제가 실제로 도는 모양

카드 결제는 생각보다 단계가 많습니다. 이 흐름만 이해하면 어느 PG를 쓰든 비슷합니다.

단계어디서무슨 일
① 주문 만들기내 서버"이 사람이 이걸 이 금액에 사려 한다"를 DB에 먼저 적는다. 주문번호를 만든다.
② 결제창 열기손님 브라우저주문번호·금액·상품명을 들고 토스 결제창을 띄운다.
③ 카드 입력토스카드사와 토스가 처리. 우리는 카드번호를 보지도 않는다.
④ 돌아오기손님 브라우저성공하면 우리가 지정한 successUrl로, 실패하면 failUrl로 돌아온다.
⑤ 승인내 서버시크릿 키로 토스에 "이 결제 진짜 맞아?"라고 물어 최종 승인한다. 여기까지 해야 결제 완료다.
⑥ 지급내 서버승인이 성공한 뒤에야 크레딧을 주거나 파일을 열어 준다.
여기서 사고가 납니다 — 꼭 지키세요

④에서 돌아온 것만 믿고 물건을 주면 안 됩니다. 브라우저 주소창은 누구나 손으로 고칠 수 있습니다. ?success=true&amount=10 같은 주소를 직접 쳐 넣으면, 검증 없는 사이트는 10원에 물건을 내줍니다.

⑤의 서버 승인이 성공했을 때만 물건을 주세요. 그리고 승인할 때 넘기는 금액은 주소창에서 받은 값이 아니라 ①에서 DB에 적어 둔 금액과 대조해야 합니다.

승인은 서버에서 이렇게 부릅니다. 어렵지 않습니다.

// adapters/payment/toss.ts (서버 전용)
const CONFIRM_URL = "https://api.tosspayments.com/v1/payments/confirm";

// Basic 인증: base64("{시크릿키}:") — 비밀번호 자리는 비운다.
const auth = Buffer.from(`${process.env.TOSS_SECRET_KEY}:`).toString("base64");

const res = await fetch(CONFIRM_URL, {
  method: "POST",
  headers: { Authorization: `Basic ${auth}`, "Content-Type": "application/json" },
  body: JSON.stringify({ paymentKey, orderId, amount }),
});

주석의 콜론(:)을 빼먹지 마세요. 시크릿 키 뒤에 콜론을 붙여서 base64로 바꿔야 합니다. 이걸 빠뜨려서 401 UNAUTHORIZED가 나는 경우가 흔합니다.

키 두 개를 구분하세요

키어디에 두나공개돼도 되나
클라이언트 키NEXT_PUBLIC_TOSS_CLIENT_KEY — 결제창을 띄우는 데 씀네. 원래 브라우저에 노출됩니다.
시크릿 키TOSS_SECRET_KEY — 서버에서 승인할 때만 씀절대 안 됩니다. NEXT_PUBLIC_을 붙이면 안 됩니다.
이 오류가 뜨면

결제창이 안 뜨고 아무 반응 없음
클라이언트 키가 비어 있는 경우가 대부분입니다. 환경변수를 넣고 다시 배포했는지 확인하세요.

손님이 결제창을 그냥 닫았는데 빨간 오류가 뜬다
취소는 오류가 아닙니다. 우리는 취소로 보이는 메시지는 화면에 띄우지 않습니다.

if (!/취소|cancel|close|USER_CANCEL/i.test(msg)) setError(msg);

승인 단계에서 시간 초과
결제 승인은 네트워크를 여러 번 왕복합니다. 서버 함수의 제한 시간을 넉넉히 주세요. 우리는 결제 관련 페이지에 export const maxDuration = 60;을 붙여 뒀습니다.

📷 캡처 필요 토스페이먼츠 개발자센터에서 테스트 키(클라이언트 키·시크릿 키)를 확인하는 화면. 시크릿 키는 일부 가려서.
수수료. PG 수수료는 업종·매출 규모·결제 수단에 따라 다르고 계약할 때 정해집니다. 이 문서에 숫자를 적어 드릴 수 없습니다 — 계약 전에 반드시 직접 확인하세요. 정산 주기(며칠 뒤에 내 통장에 들어오는지)도 함께 물어보세요. 생각보다 늦습니다.

무료 스톡 (Unsplash, Pexels 등)공짜, 품질 좋음.남들도 다 씀. 톤이 제각각. 원하는 장면이 없음.
AI 생성 (힉스필드 등)원하는 장면을 원하는 톤으로. 영상까지.손·글자가 깨질 때가 있음. 요금이 듦.

우리는 힉스필드(Higgsfield)로 이미지와 짧은 영상을 만듭니다. 홈페이지의 분위기 컷, 마케팅 카드뉴스, SNS 릴스가 여기서 나옵니다.

실제로 써 보고 배운 요령

  • 한 장씩 뽑지 말고 "한 벌"로 뽑으세요. 사이트 안의 이미지가 톤이 제각각이면 오히려 더 어수선해 보입니다. 조명·색감·화각을 문장으로 고정해 두고(예: "따뜻한 자연광, 종이 질감, 카메라는 눈높이") 그 문장을 모든 컷에 그대로 붙이세요.
  • 글자는 AI에게 맡기지 마세요. 이미지 안에 한글을 넣으라고 하면 거의 깨집니다. 배경만 AI로 만들고 글자는 화면(HTML/CSS)에서 얹으세요. 나중에 문구를 고칠 때도 훨씬 편합니다.
  • 사람 얼굴은 조심스럽게. 실제 인물처럼 보이는 이미지를 후기·직원 사진처럼 쓰면, 손님이 알아챘을 때 신뢰가 통째로 무너집니다. 분위기 컷이나 뒷모습·손·사물 위주로 쓰세요.
  • 가로/세로를 미리 정하세요. 웹 배너는 가로로 길고(예: 16:9, 21:9), SNS는 정사각이나 세로(1:1, 9:16)입니다. 나중에 자르면 중요한 부분이 잘립니다.
  • 영상은 3~6초짜리 여러 개가 낫습니다. 긴 영상 하나보다 짧은 걸 이어 붙이는 편이 실패해도 다시 뽑기 쉽습니다.

사이트에 넣을 때 — 무거우면 안 넣느니만 못합니다

AI가 준 이미지는 대개 아주 큽니다(수 MB). 그대로 올리면 사이트가 눈에 띄게 느려집니다.

  • 형식은 WebP나 AVIF로. 같은 화질에 용량이 훨씬 작습니다. Next.js를 쓴다면 next/image가 알아서 변환·크기 조절을 해 줍니다. <img> 대신 그걸 쓰세요.
  • 표시할 크기보다 조금만 크게. 화면에 400px로 나오는 이미지를 4000px로 올릴 이유가 없습니다.
  • 영상은 자동재생 + 음소거 + 반복이 기본입니다. 소리가 갑자기 나오면 손님은 탭을 닫습니다.
권리와 요금. AI로 만든 이미지·영상을 상업적으로 써도 되는지, 어디까지 되는지는 도구마다 다르고 요금제마다 다릅니다. 자주 바뀌기도 합니다. 쓰기 전에 그 도구의 약관과 요금 안내를 직접 확인하세요. 특히 유료 상품에 넣거나 광고에 쓸 계획이면 반드시요.
📷 캡처 필요 힉스필드에서 같은 톤 지시문으로 여러 컷을 뽑아 나란히 놓은 결과. "한 벌로 뽑는다"가 눈으로 보이게.

AI 기능 붙이기 (Claude API)

언제 필요한가 — 손님이 내 사이트 안에서 AI를 쓰게 하고 싶을 때

지금까지는 내가 AI로 사이트를 만들었습니다. 이 장은 손님이 내 사이트 안에서 AI를 쓰게 하는 이야기입니다. 요약해 주는 기능, 문구를 만들어 주는 기능 같은 것들이요.

1) 키 받아서 숨기기

  1. console.anthropic.com에 가입하고, 결제 수단을 등록한 뒤 API Key를 만듭니다. (쓴 만큼 내는 방식입니다.)
  2. 키를 .env.local과 Vercel 환경변수에 넣습니다.
ANTHROPIC_API_KEY=sk-ant-...
이것만은 꼭

이 키에 NEXT_PUBLIC_을 붙이면 안 됩니다. 그 순간 브라우저에서 누구나 볼 수 있게 되고, 남이 당신 카드로 AI를 씁니다. 실제로 자주 벌어지는 사고입니다.

AI 호출은 반드시 서버에서만 하세요. Next.js라면 서버 컴포넌트, 서버 액션, 또는 app/api/... 안입니다. 화면 쪽 코드("use client"가 붙은 파일)에서는 절대 부르지 마세요.

2) 부르기

npm install @anthropic-ai/sdk

이건 이런 뜻이에요. "Claude를 쉽게 부를 수 있는 도구를 설치해라."

// 서버 쪽 파일에서만
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });

const message = await client.messages.create({
  model: "claude-haiku-4-5",
  max_tokens: 4000,
  system: "너는 ~를 하는 도우미다. 결과는 JSON으로만 답한다.",
  messages: [{ role: "user", content: 사용자입력 }],
});

세 개만 알면 됩니다. model = 어떤 모델을 쓸지. max_tokens = 답을 최대 얼마나 길게 쓸지. system = "너는 이런 역할이다"라는 사전 지시. messages에 실제 질문이 들어갑니다.

3) 모델은 일마다 다르게 — 이게 원가를 정합니다

모델은 여러 개고, 똑똑할수록 비쌉니다. 모든 걸 제일 비싼 모델로 하면 원가가 무너집니다.

우리는 이렇게 나눴습니다.

하는 일쓰는 모델왜
화면 목록 뼈대 만들기빠르고 싼 모델 (Haiku)양이 많고 형식이 정해져 있다. 속도와 값이 중요.
내용을 깊게 보강하기비싼 모델 (Opus)판단이 필요하다. 결과 품질이 곧 상품 가치.
검수(잘못된 곳 찾기)비싼 모델 (Opus)놓치면 안 되는 일이라 값보다 정확도.
요금. 모델별 단가(입력·출력 토큰당 가격)는 바뀝니다. Anthropic 공식 요금 페이지에서 직접 확인하세요. 다만 방향은 확실합니다 — 같은 일을 시켜도 모델에 따라 원가가 몇 배 차이 납니다.
우리가 겪은 것

AI 기능을 붙일 때 아무도 미리 안 알려 주는 세 가지

① 오래 걸립니다. 그리고 서버가 먼저 포기합니다.
Vercel 같은 곳의 서버 함수는 기본 제한 시간이 짧습니다. AI가 긴 답을 쓰는 데 1~2분이 걸리면, 답이 오기도 전에 서버가 끊어 버립니다. 손님 화면엔 그냥 오류가 뜨죠. 우리는 무거운 화면마다 제한 시간을 직접 올려 뒀습니다.

// 이 페이지/경로는 최대 300초까지 기다린다
export const maxDuration = 300;

다만 얼마까지 올릴 수 있는지는 요금제마다 다릅니다. Vercel 문서에서 확인하세요. 그리고 화면에는 반드시 "만드는 중이에요" 표시를 두세요. 1분 넘게 아무 반응이 없으면 손님은 고장 났다고 생각하고 새로고침합니다.

② 답이 중간에 잘립니다. 그런데 오류가 안 납니다.
max_tokens에 걸리면 AI는 문장 한가운데서 그냥 멈춥니다. JSON을 달라고 했다면 닫는 괄호가 없는 반쪽짜리 JSON이 옵니다. 이걸 그대로 쓰면 엉뚱한 데서 터지고, 원인을 찾는 데 하루가 갑니다.

반드시 왜 멈췄는지를 확인하고, 잘렸으면 그 묶음은 버리세요.

// 분량 상한에 걸려 JSON이 잘린 경우 — 이 결과는 신뢰할 수 없다
if (message.stop_reason === "max_tokens") {
  throw new Error("TRUNCATED");
}

덧붙여, 한 번에 너무 많은 걸 시키지 마세요. 우리는 "① 뼈대만 만들기 → ② 화면별 내용 채우기"로 두 단계로 쪼갰고, ②는 다시 여러 묶음으로 나눠 부릅니다. 그러면 한 묶음이 실패해도 전체를 버리지 않아도 됩니다.

③ 얼마 썼는지 모르면 값을 못 매깁니다.
AI를 쓰는 기능으로 돈을 받으려면 한 번 실행에 얼마가 드는지를 알아야 합니다. 그런데 이건 청구서가 와야 아는 게 아니라, 호출할 때마다 응답에 들어 있습니다. 우리는 매 호출의 토큰 사용량을 모아서 로그에 한 줄로 찍습니다.

const u = message.usage;
usage.input      += u.input_tokens ?? 0;
usage.output     += u.output_tokens ?? 0;
usage.cacheRead  += u.cache_read_input_tokens ?? 0;
usage.cacheWrite += u.cache_creation_input_tokens ?? 0;

이 숫자를 며칠만 모아 보면 "이 기능은 1회에 대략 얼마"가 나옵니다. 그 값을 알고 나서 가격을 정하세요. 우리는 이걸 안 하다가 큰 프로젝트에서 적자를 냈고, 이후로 "실행 규모에 비례하는" 방식으로 값을 다시 짰습니다.

이 오류가 뜨면

401 authentication_error
키가 없거나 틀렸습니다. Vercel에 넣었다면 재배포했는지 확인하세요.

429 rate_limit_error
너무 빨리 많이 불렀습니다. 잠깐 쉬었다 다시 시도하는 처리를 넣으세요.

JSON을 달라고 했는데 "네, 알겠습니다"가 앞에 붙어 온다
흔한 일입니다. 응답 문자열에서 첫 {와 마지막 } 사이만 잘라 쓰면 안전합니다.

안 망가지게 지키기

언제 필요한가 — 한 군데 고칠 때마다 다른 데가 깨질 때

사이트가 커지면 반드시 이 순간이 옵니다. 버튼 색 하나 바꿨는데 결제가 안 되고, 그걸 손님이 먼저 알려 줍니다. 개발자가 아니어도 막을 방법이 있습니다.

1) 올릴 때마다 자동으로 검사받기 (GitHub Actions)

깃허브에는 "코드가 올라오면 자동으로 뭔가 시키는" 기능이 있습니다. 제일 값진 건 "일단 지어지기는 하는지"를 확인하는 겁니다.

프로젝트에 .github/workflows/ci.yml 파일을 만들고 아래를 넣으세요. 우리 것과 거의 같습니다.

name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build-and-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - name: Build
        run: npm run build

이건 이런 뜻이에요. "main에 코드가 올라오거나 변경 제안이 생기면, 깨끗한 리눅스 컴퓨터를 하나 빌려서 → 코드를 받고 → Node 20을 깔고 → 부품을 설치하고 → 사이트를 지어 봐라." 짓다가 실패하면 깃허브에 빨간 X가 뜹니다.

이것만으로도 "빌드도 안 되는 코드를 실서버에 올리는" 사고의 대부분이 막힙니다.

📷 캡처 필요 GitHub Actions 탭에서 CI가 초록 체크로 통과한 화면과, 실패해서 빨간 X가 뜬 화면 두 장.

2) 지켜야 할 규칙을 기계에게 맡기기

우리는 검사를 하나 더 넣었습니다.

      - name: Enforce domain/adapters boundary
        run: npm run depcruise

이게 무슨 일이냐면. 우리 코드는 "핵심 규칙" 부분과 "바깥 세상과 연결하는" 부분이 나뉘어 있습니다. 핵심 규칙 쪽에서 결제 회사나 데이터베이스를 직접 부르면 안 되죠. 그런데 사람은 잊습니다. 그래서 규칙을 어긴 코드가 올라오면 자동으로 빨간 X가 뜨게 만들었습니다.

여러분의 프로젝트에 이걸 그대로 넣을 필요는 없습니다. 핵심은 "지키기로 한 규칙을 사람의 기억이 아니라 기계에 맡긴다"는 겁니다.

3) 진짜 주소에 올리기 전에 미리 보기

Vercel은 변경 제안(Pull Request)마다 임시 주소를 하나씩 만들어 줍니다. 실제 사이트는 그대로 두고, 그 임시 주소에서 먼저 눌러 볼 수 있습니다.

습관을 이렇게 바꾸면 사고가 확 줍니다.

  1. main에 바로 올리지 않고 가지(branch)를 하나 파서 작업합니다.
  2. 변경 제안을 올리면 CI 검사가 돌고, Vercel이 미리보기 주소를 답니다.
  3. 그 주소에서 직접 눌러 보고, 괜찮으면 합칩니다.
git switch -c fix-login
# ... 고치고 ...
git add .
git commit -m "로그인 버튼 문구 수정"
git push -u origin fix-login

이건 이런 뜻이에요. "fix-login이라는 새 가지를 만들어 거기서 작업하고, 그 가지를 창고에 올려라." 올리면 깃허브가 "변경 제안을 만들까요?"라고 물어봅니다.

4) 잘못 올렸을 때 — 되돌리기

Vercel의 Deployments 탭에는 지금까지 올린 것들이 전부 남아 있습니다. 멀쩡했던 것을 골라 ⋯ → Promote to Production(또는 Instant Rollback)을 누르면 몇 초 만에 그 상태로 돌아갑니다. 코드를 고치는 게 아니라 예전에 지어 둔 것으로 스위치를 옮기는 것이라 아주 빠릅니다.

문제가 생기면 원인부터 찾지 말고 일단 되돌리세요. 손님이 오류를 보고 있는 시간을 줄이는 게 먼저입니다. 원인은 그다음에 찾으면 됩니다.

5) 위험한 것은 스위치 뒤에 두기

6장에서 만든 스위치는 결제만을 위한 게 아닙니다. 아직 자신 없는 기능은 만들어 두되 꺼 두세요. 우리는 화면을 직접 편집하는 기능을 다 만들어 놓고 껐습니다.

/**
 * 화면 목록에서 화면을 직접 고칠 수 있게 하는가.
 *
 * 잘 쓰려면 기획 감각이 필요해 대부분의 사용자에게는 부담이었다(2026-08-03 보류).
 * 기능은 그대로 두고 버튼만 감춘다 — 다시 열 때 이 값만 true로 바꾸면 된다.
 */
export const SCREEN_EDIT_OPEN = false;

지우지 않고 끄는 이유. 지우면 다시 만들어야 하고, 나중에 "왜 없앴더라"를 아무도 기억 못 합니다. 꺼 두고 이유를 적어 두면 언제든 한 줄로 되살릴 수 있습니다.

오류가 났는데 뭐가 문제인지 모를 때

Vercel 프로젝트의 Logs(또는 각 배포의 Runtime Logs)를 보세요. 손님 화면엔 "오류가 발생했습니다"만 나와도, 여기엔 진짜 이유가 한 줄로 찍혀 있습니다. 그 줄을 그대로 복사해서 AI에게 물어보면 대개 바로 답이 나옵니다.

  • http://로 들어가도 https://로 넘어간다.

로그인

  • 화면에 보이는 소셜 로그인 버튼이 전부 실제로 동작한다(4장).
  • 로그아웃이 된다. 조용히 실패하지 않는다(3장의 함정).
  • 로그아웃 상태로 회원 전용 주소를 직접 쳐서 들어가면 막힌다.
  • 다른 사람의 데이터 주소를 직접 쳐 넣어도 안 보인다. (남의 프로젝트 번호로 바꿔 보세요.)

결제 (받는다면)

  • 실제 카드로 최소 금액 한 번 결제해 본다. 테스트 키로 백 번 해 본 것과 다릅니다.
  • 결제 후 물건(크레딧·파일·권한)이 실제로 들어온다.
  • 결제창을 그냥 닫았을 때 빨간 오류가 안 뜬다.
  • 취소·환불을 어떻게 처리할지 내가 알고 있다.
  • 푸터에 상호·대표자·사업자등록번호·통신판매업 신고번호·주소·연락처가 있다.
  • 이용약관과 개인정보처리방침 링크가 있고, 내용이 실제와 맞다(체험 기간·환불 조건 등).

화면

  • 휴대폰으로 전부 열어 본다. 가로로 밀리는 화면이 없다.
  • 목록에 아무것도 없을 때(빈 화면)가 깨져 보이지 않는다.
  • 없는 주소를 쳤을 때 404 화면이 제대로 나온다.
  • 오래 걸리는 동작에 "처리 중" 표시가 있다(8장).
  • 회색 네모, lorem ipsum, "여기에 텍스트" 같은 임시 내용이 남아 있지 않다.
  • 카카오톡·슬랙에 주소를 붙였을 때 미리보기 카드가 제대로 나온다.

안 보이는 것

  • 깃허브 창고에 .env나 키 파일이 올라가 있지 않다(1장).
  • 브라우저 개발자 도구에서 시크릿 키가 안 보인다(NEXT_PUBLIC_ 점검).
  • 문의받을 창구(메일·카톡 등)가 있고, 내가 그걸 실제로 본다.
  • 데이터베이스 백업/브랜치를 어떻게 하는지 안다(5장).
  • 문제가 생겼을 때 되돌리는 법을 안다(9장).
