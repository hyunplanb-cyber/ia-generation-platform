# IA 자동생성 플랫폼 PRD

## 1. 배경 및 문제 정의

웹사이트/서비스를 기획할 때 기획자는 항상 세 가지 산출물을 만든다: **IA(정보구조)**, **화면별 기능정의서**, **WBS(작업일정)**. 이 세 문서는 서로 강하게 연결되어야 하지만(어떤 화면이 어떤 일정에 만들어지는지, 어떤 요구사항이 어떤 화면에 반영되는지), 실제로는 대부분 엑셀로 각각 따로 작성되고 손으로 동기화된다. 참고용으로 확보한 실제 산출물 샘플 3종(WBS/요구사항정의서/코오롱스포츠 IA — 서로 다른 프로젝트에서 나온 별개의 문서로, 상호 연결된 세트는 아님)은 각 문서 유형이 실무에서 어떤 컬럼/ID 체계로 작성되는지 보여주는 형식 참고 자료로만 활용한다. 상세 구조는 [addendum.md §A] 참조.

동시에, 생성형 AI로 웹 프로젝트를 만드는 경우가 늘고 있는데, AI 코딩 도구(Claude Code, Cursor 등)에 "이 화면을 만들어줘" 식으로 던지는 프롬프트의 품질이 결과물 품질을 좌우한다. 그런데 이런 화면별 프롬프트를 구조화해서 뽑아주는 도구가 없다.

**본 플랫폼은 기획자(또는 기획 지식이 부족한 창업자)가 사이트 컨셉과 메뉴 구조만 입력하면, IA·화면별 기능정의·화면별 일정·화면별 AI 프롬프트를 자동으로 생성하고, 이를 엑셀로 내보내 AI 코딩 도구에 바로 활용할 수 있게 하는 웹 서비스다.**

## 2. 목표 (Goals)

- 기획자가 수작업으로 며칠씩 걸리던 "메뉴 구조 → 화면 리스트 → 기능정의 → 일정 산정"을 몇 분 안에 초안으로 생성한다.
- 생성된 산출물이 AI 코딩 도구에 바로 활용 가능한 수준의 화면별 프롬프트를 포함한다.
- 산출물은 100% 사용자가 수정 가능해야 한다 — 자동생성은 "완성본"이 아니라 "빠른 초안"이다.
- 장기적으로 실제 배포/수익화가 가능한 서비스로 발전한다 (계정 시스템, 다중 프로젝트, 향후 결제 확장을 고려한 구조로 설계).

### 비목표 (Non-goals, 이번 릴리즈)

- 결제/과금 모델 확정 및 구현 (계정 시스템은 포함하되 결제 연동은 범위 밖)
- 실시간 공동편집(멀티유저 동시 편집)
- 실제 화면 디자인/와이어프레임 생성 (본 플랫폼은 "정의서"까지이며 비주얼 목업은 만들지 않음)
- IA/요구사항/WBS 외 산출물(예: 데이터베이스 설계서, API 명세서)
- 엑셀 재업로드(임포트) — 내보내기 전용. 외부에서 수정한 엑셀을 다시 반영하는 기능은 제공하지 않는다.

## 3. 타겟 사용자

두 세그먼트를 동시에 만족시킨다 (사용자 확정: 좁히지 않고 넓게 간다).

- **전문 기획자/PM** (에이전시, 인하우스 서비스기획팀): 이미 IA/기능정의/WBS를 작성해본 경험이 있고, 속도와 정합성(산출물 간 정합, 엑셀 포맷 호환)을 중시한다.
- **비전문가 창업자/마케터**: 기획 방법론을 모르지만 AI로 빠르게 프로젝트를 만들고 싶어한다. 가이드형 UX와 "일단 그럴듯한 초안"이 중요하다.

두 세그먼트가 요구하는 것이 다를 수 있으므로 (전문가는 세밀한 커스터마이징, 비전문가는 쉬운 기본값), UX 단계에서 "간단 모드/상세 모드" 같은 분기가 필요할 수 있다 — `[NOTE FOR PM/UX]` 상세 설계는 `bmad-ux` 단계로 위임.

## 4. 경쟁 환경과 차별화

시장에는 IA만 만들어주는 도구(Octopus.do, Relume 등), 일정만 만들어주는 AI WBS 도구, 스펙-투-코드 도구(Specifys.ai, Kiro 등)가 각각 존재하지만, **IA + 화면별 기능정의 + 화면별 AI 프롬프트 + 화면별 일정을 "화면" 단위로 하나로 묶은 도구는 없다.** 한국어/엑셀 네이티브 산출물이라는 점도 기존 도구 대비 공백이다. 상세 리서치는 [addendum.md §B] 참조.

**포지셔닝**: "기획과 AI 코딩 도구 사이의 빠진 중간 계층."

## 7. 기능 요구사항 (Functional Requirements)

### 7.1 프로젝트/컨셉 관리

- **FR-1**: 사용자는 로그인 후 새 프로젝트를 생성할 수 있다. 프로젝트는 컨셉/설명, 전체 프로젝트 시작일·종료일(전체 일정)을 포함한다.
- **FR-2**: 사용자는 여러 개의 프로젝트를 계정 아래에 만들고 목록에서 관리(조회/수정/삭제)할 수 있다.
- **FR-3**: 프로젝트의 전체 일정은 이후 화면별 일정 자동 산정의 기준값으로 쓰이며, 언제든 수정 가능하고 수정 시 화면별 일정 재계산을 트리거할 수 있다 (사용자 확인 후 적용 — 수동 수정분을 덮어쓰지 않도록 경고).

### 7.2 메뉴 입력

- **FR-4**: 사용자는 프로젝트 내에서 메뉴를 여러 개 추가할 수 있다. 각 메뉴는 다음을 포함한다: 메뉴명(한글), 메뉴명 영문 표기(메뉴코드 자동 산출의 근거), 설명, 원하는 기능(자유서술 또는 태그형 선택).
- **FR-5**: 메뉴명 영문 표기로부터 **메뉴코드**를 자동 산출한다 (영문 메뉴명 앞 2글자, 대문자 — 예: MEMBER → MR). 다음 경우 자동 산출을 거부하고 수동 입력을 요구한다: (1) 다른 메뉴의 코드와 중복되는 경우 `[ASSUMPTION]`, (2) 영문 표기가 1글자뿐이어서 2글자 코드를 만들 수 없는 경우, (3) 디바이스코드 예약어(`PC`, `MO`)와 동일한 코드가 산출되는 경우 (예: "Product Care"→`PC`는 페이지ID 파싱을 모호하게 만듦).
- **FR-6**: 메뉴 목록은 순서 변경, 수정, 삭제가 가능하다.
  - **메뉴 삭제 시**: 해당 메뉴에 속한 화면은 즉시 삭제하지 않고 "소속 메뉴 삭제됨" 상태로 격리 보관한다. 사용자는 격리된 화면을 확인 후 직접 삭제하거나 다른 메뉴로 재배정할 수 있다. 삭제된 화면의 페이지ID를 참조하던 다른 화면의 버튼 이동 링크는 FR-11의 "깨진 링크" 규칙을 따른다.
  - **메뉴코드 변경 시**: 이미 발급된 페이지ID는 소급 변경하지 않는다(기존 화면 유지). 이후 신규 생성되는 화면부터 새 코드가 적용되며, 같은 메뉴 내에 신/구 코드가 혼재할 수 있음을 화면 목록에 경고 표시한다.

### 7.3 IA 생성 실행

- **FR-7**: 사용자가 **[실행: IA 생성]** 버튼을 클릭하면, 등록된 모든 메뉴를 기준으로 필요한 화면(페이지) 목록을 자동 생성한다. 생성 로직은 메뉴별 "원하는 기능" 서술을 분석하여 통상적으로 필요한 화면 세트(목록/상세/등록/수정/완료/에러·빈상태 등)를 추론한다 — 최초 버전은 규칙기반 패턴 매칭(예: "장바구니"→상품있음/없음 상태 화면 2종, "회원가입"→약관동의/정보입력/완료 화면 3종 등 도메인 패턴 라이브러리 사용) `[ASSUMPTION: 패턴 라이브러리는 커머스/회원/게시판 등 흔한 도메인 위주로 초기 구축, 지속 확장]`.
  - **완료 기준**: (1) 등록된 메뉴 각각에 대해 최소 1개 이상의 화면이 생성된다. (2) 도메인 패턴 라이브러리에 매칭되는 메뉴는 해당 패턴의 표준 화면 세트가, 매칭되지 않는 메뉴는 범용 기본 화면 세트(목록형 또는 단일 화면 — 매칭 실패 시 폴백)가 생성된다. (3) 생성 직후 페이지ID 중복이 0건이어야 한다(FR-9 고유성 검증 통과). (4) 생성된 화면 각각은 FR-9~FR-13의 5개 항목이 최소 기본값(빈 값이 아닌 자동 초안)으로 채워진 상태로 반환된다.
- **FR-8**: 재실행([실행: IA 생성]을 다시 클릭) 시 기존에 사용자가 수동으로 수정한 화면 데이터는 보존하고, 신규로 추가된 메뉴/변경분에 대해서만 화면을 추가 생성한다 (전체 덮어쓰기 금지) `[ASSUMPTION]`. 화면이 수동 수정되었는지 여부는 NFR-7의 감사 추적 플래그로 판별한다. 메뉴 삭제로 격리된 화면(FR-6)은 재실행 대상에서 제외한다.

### 7.4 화면(페이지) 단위 관리 — 핵심 데이터 모델

생성된 각 화면은 다음 5개 항목을 가지며, **모두 사용자가 화면에서 직접 수정 가능해야 한다.**

- **FR-9: 페이지ID**
  - 규칙: `{디바이스코드}{메뉴코드}{일련번호}` (예: `PCMR1000`, 또는 디바이스 구분이 없는 프로젝트는 `MR1000`).
  - 메뉴코드: 영문 메뉴명 앞 2글자 (FR-5).
  - 일련번호: 4자리, 10 단위로 증가(1000, 1010, 1020…)하여 추후 화면 삽입 여지를 남긴다 `[ASSUMPTION — 참고: addendum.md의 실제 IA 파일은 대/소 일련번호 2단 구성을 쓰기도 함. MVP는 단순 4자리 채택, 필요시 확장]`.
  - 디바이스코드: 프로젝트 설정에서 "PC/모바일 반응형 단일" vs "PC/모바일 완전 분리" 여부를 선택하게 하고, 분리형일 때만 디바이스코드를 페이지ID에 포함한다. 분리형인 경우 PC/모바일 화면이 쌍으로 존재하지 않을 수 있음을 허용한다(한쪽만 존재 가능) — [addendum.md §A-3]의 실사례(`-` 표기)를 참고한 설계.
  - **디바이스 대응 방식을 화면 생성 이후에 변경하는 경우**: 이미 발급된 페이지ID는 소급 변경하지 않는다. 이후 신규 생성/추가되는 화면부터 새 방식이 적용되며, 프로젝트 내 신/구 방식의 화면이 혼재할 수 있음을 화면 목록 상단에 경고 배너로 알린다. 기존 화면을 새 방식에 맞게 일괄 변환하는 기능은 이번 범위 밖이며 필요 시 사용자가 수동으로 재정의한다.
  - 페이지ID는 사용자가 직접 수정 가능하나, **같은 프로젝트 내에서 고유**해야 한다(중복 검증). 프로젝트가 다르면 동일한 페이지ID가 발생할 수 있다(FR-5의 메뉴코드가 프로젝트 스코프이므로 페이지ID도 동일 스코프로 정합).

- **FR-10: 페이지명**
  - 규칙: `메뉴명 + 상태/행위` (예: "장바구니 상품있음", "장바구니 상품없음").
  - 자동생성값은 수정 가능한 텍스트 필드로 제공.

- **FR-11: 화면기능정의**
  - 화면 내 주요 기능/구성요소를 목록화한다.
  - 화면 내 버튼/액션 요소별로 "선택 시 발생하는 동작 또는 이동 대상 화면ID"를 명시한다 (예: "주문하기 버튼 → OD1000 주문하기 화면으로 이동"). 이동 대상은 같은 프로젝트 내 다른 페이지ID를 참조/링크할 수 있어야 한다 (드롭다운 또는 자동완성으로 페이지ID를 선택하게 하여 오타/깨진 링크 방지) `[ASSUMPTION]`.
  - **깨진 링크 처리**: 참조 대상 페이지ID가 삭제되거나 다른 값으로 변경되면 해당 버튼-액션 항목은 자동으로 삭제·재연결되지 않고 "깨진 링크" 경고 배지로 표시된다. 사용자가 수동으로 재연결하거나 항목을 정리해야 한다. 화면 목록/엑셀 내보내기에서도 깨진 링크 여부를 표시한다.
  - 자유 텍스트 + 구조화된 "버튼-액션" 리스트 항목의 혼합 형태로 편집 가능해야 한다.

- **FR-12: AI프롬프트**
  - MVP: 페이지명, 화면기능정의, 메뉴 설명/원하는 기능, 같은 메뉴의 다른 화면, 전체 사이트 컨셉을 맥락으로 넘겨 **Claude API(Haiku 4.5)** 를 호출해 화면별 프롬프트를 생성한다. 규칙기반 템플릿 초안 없이 처음부터 실제 LLM 생성으로 시작한다(원가가 프로젝트당 100~300원 수준으로 확인되어 단계적으로 갈 이유가 없음).
  - API 실패/장애 시 폴백은 Architecture 단계에서 결정(예: 재시도 후 실패 안내, 또는 최소한의 규칙기반 문구로 대체) — 이번 PRD 정정에서는 "무엇으로 생성하는가"만 확정하고 장애 처리 세부는 열어둔다.
  - 자동생성 프롬프트는 전체 텍스트 편집이 가능해야 한다.

- **FR-13: 일정**
  - 프로젝트 전체 일정(FR-1)과 화면 수를 기준으로 화면별 제작 시작일/종료일을 자동 분배한다. 초기 로직은 균등분배를 기본으로 하되, 메뉴 우선순위나 화면 복잡도(기능정의 항목 수 등)에 따라 가중치를 둘 수 있다 `[ASSUMPTION — 정교한 산정 알고리즘은 Phase 2, MVP는 균등분배+수동조정을 우선]`.
  - 각 화면의 일정은 개별적으로 수동 수정 가능하며, 수동 수정된 화면은 전체 일정 재계산(FR-3) 시 보호된다.
  - 화면 간 일정 겹침/역전(선행 화면 일정이 후행 화면보다 늦게 끝나는 경우 등)에 대한 경고 표시 `[ASSUMPTION, 상세 로직은 UX/Architecture 단계에서 구체화]`.
  - **전체 일정 단축 시 충돌 처리**: 전체 프로젝트 일정이 줄어들어 이미 수동 수정된 화면 일정이 새 범위를 벗어나게 되는 경우, 자동으로 덮어쓰거나 잘라내지 않는다. 해당 화면들을 "범위 이탈" 상태로 표시하여 목록 상단에 모아 보여주고, 사용자가 건별로 조정하거나 유지할지 결정하게 한다.

### 7.5 산출물 내보내기

- **FR-14**: 프로젝트의 전체 화면 리스트(페이지ID/페이지명/화면기능정의/AI프롬프트/일정 전체 컬럼)를 엑셀(.xlsx)로 다운로드할 수 있다. [실행: IA 생성](FR-7) 처리가 진행 중인 동안에는 다운로드 버튼을 비활성화하여, 생성 도중의 불완전한 스냅샷이 내려받아지지 않게 한다.
- **FR-15**: 내보내기 포맷은 [addendum.md §A]에서 확인한 업계 관행(1~5 Depth 브레드크럼 컬럼, 디바이스별 병행 표기)과 정합하도록 설계하여, 기존 기획 문서에 익숙한 사용자가 바로 알아볼 수 있게 한다.
- **FR-16**: 화면 리스트뿐 아니라 메뉴 목록, 프로젝트 개요도 별도 시트로 함께 내보낸다 `[ASSUMPTION]`.

### 7.6 플랫폼 자체 UI

- **FR-17**: 플랫폼은 일반적인 서비스형 웹사이트 형태로 **GNB(상단 내비게이션)**와 **푸터**를 포함한다 (로고/메뉴/로그인상태/이용약관·개인정보처리방침 링크 등 표준 구성) `[ASSUMPTION: 상세 메뉴 구성은 UX 단계에서 확정]`.

### 7.7 계정/인증

- **FR-18**: 신규 가입/로그인 기능을 제공하며 (사용자 확정: 로그인 필수), 프로젝트는 계정에 귀속되어 클라우드에 저장된다. 계정 삭제(탈퇴) 시 프로젝트를 즉시 삭제하지 않고 유예 기간(30일) 동안 보관하며, 유예 기간 중 엑셀 내보내기를 안내한다 `[ASSUMPTION]`. 프로젝트 소유권 이전/공유는 이번 범위 밖(§10 열린 질문 참조).
- **FR-19**: 계정 시스템은 향후 결제/구독 연동을 전제로 설계한다 (예: 플랜/권한 필드를 확장 가능하게) — 결제 자체는 이번 범위 밖.

### 7.8 AI프롬프트 품질 피드백

- **FR-20**: 각 화면의 AI프롬프트에 대해 사용자가 👍/👎 피드백을 남길 수 있다. 이 피드백은 섹션 5의 "핵심가치 검증" 지표(AI프롬프트 만족도)의 직접 데이터 소스가 된다.

## 8. 비기능 요구사항 (NFR)

- **NFR-1 (보안)**: 로그인 기반 서비스이므로 비밀번호 저장(해시), 세션/토큰 관리, 프로젝트 데이터 접근권한(본인 프로젝트만 조회/수정 가능)을 표준 보안 관행에 따라 구현한다.
- **NFR-2 (데이터 내구성)**: 사용자가 입력/수정한 데이터(특히 수동 수정한 페이지 정보)는 자동생성 로직 재실행으로 유실되지 않아야 한다 (FR-8, FR-13 참조).
- **NFR-3 (성능)**: 메뉴 수/화면 수가 많은 대형 프로젝트(예: 100+ 화면)에서도 IA 생성 실행과 엑셀 다운로드가 수용 가능한 시간 내(수 초~수십 초) 완료되어야 한다 `[ASSUMPTION: 구체적 SLA는 Architecture 단계에서 확정]`.
- **NFR-4 (호환성)**: 내보낸 엑셀 파일은 Microsoft Excel 및 Google Sheets에서 깨짐 없이 열려야 한다 (병합 셀 남용 지양).
- **NFR-5 (언어)**: 서비스 UI 및 산출물은 한국어를 기본으로 한다.
- **NFR-6 (확장성)**: 결제/구독(Phase 2)이 추가되어도 기존 데이터 모델(프로젝트/메뉴/화면)을 깨지 않고 확장 가능한 구조로 설계한다.
- **NFR-7 (감사가능성)**: 화면 데이터의 자동생성 여부와 수동 수정 여부를 구분해서 추적할 수 있어야 한다 (재생성 시 보호 로직의 전제조건, FR-8/FR-13).
- **NFR-8 (텍스트 길이 제한)**: 화면기능정의·AI프롬프트 입력 필드는 최대 길이를 두어 엑셀 셀 문자 한도(32,767자)를 넘지 않도록 UI 단에서 경고하고 초과 입력을 막는다.

## 9. 핵심 사용자 흐름 (User Journey)

1. 로그인 → 새 프로젝트 생성 → 컨셉/설명 + 전체 일정 입력 (FR-1)
2. 메뉴 추가 반복: 메뉴명/설명/원하는 기능 입력 (FR-4)
3. **[실행: IA 생성]** 클릭 → 메뉴별 화면 리스트 자동 생성 (FR-7)
4. 생성된 화면 리스트를 검토하며 페이지ID/페이지명/기능정의/AI프롬프트/일정을 필요한 만큼 수정 (FR-9~13)
5. 엑셀로 다운로드 (FR-14)
6. (플랫폼 밖) 다운로드한 엑셀/화면별 AI프롬프트를 Claude Code 등 AI 코딩 도구에 입력하여 실제 화면 제작

## 10. 열린 질문 (Open Questions)

- **[미해결]** IA 생성 알고리즘(FR-7)의 도메인 패턴 라이브러리를 어디까지 사전 구축할 것인가 (커머스/회원/게시판 외 추가 도메인 우선순위) — Architecture/UX 단계에서 구체화 필요.
- **[미해결]** 일정 자동분배(FR-13) 알고리즘의 구체적 로직(균등 vs 가중치) — Phase 1에서는 균등분배로 단순화하고 사용자 피드백을 본 뒤 고도화 여부 결정.
- **[미해결]** 무료/유료 구분 없이 전체 기능을 열어둘지, 아니면 계정 생성만으로 기능 제한 없이 쓰게 할지 — 결제 모델이 미정이므로 일단 전체 무료로 가정하고 추후 별도 논의.
- **[미해결]** 재생성(FR-8)으로 신규 화면이 추가될 때, 전체 일정에 여유 슬롯이 없으면 신규 화면의 일정을 어떻게 산정할지(기존 일정 압축/프로젝트 종료일 이후로 연장/미배정으로 남김) — Architecture 단계에서 결정.
- **[미해결]** 동일 사용자가 같은 프로젝트를 여러 탭/기기에서 동시에 열었을 때의 저장 충돌 처리(마지막 저장 우선 vs 충돌 감지 경고) — 실시간 공동편집(멀티유저)은 비목표이지만 이 단일 사용자·다중 세션 케이스는 별도로 Architecture 단계에서 다뤄야 함.
- **[미해결]** 프로젝트 소유권 이전/공유 수단 부재 — 담당자 교체가 잦은 에이전시 사용자에게는 리스크. 협업 비목표와는 별개 사안으로, Phase 3에서 "공유(읽기전용)" 정도의 경량 기능 우선 검토 후보.
- **[보류]** 팀 협업(여러 명이 한 프로젝트를 함께 편집)은 비목표로 뒀으나, 에이전시 타겟 사용자에게는 중요할 수 있음 — Phase 3 후보로 재검토.
