# 적대적 검토 (일관성 공격) — IA 자동생성 플랫폼

## Overall verdict

AD-1~7은 "무엇을 하면 안 되는가"를 각각 개별적으로는 명확히 서술하지만, **경계선상의 실제 구현 결정**(누가 플래그를 갱신하는가, 포트에 무엇이 오가는가, "미들웨어"가 코드로 무엇인가, ID가 FK인지 문자열인지)을 규정하지 않아 두 독립된 빌더가 각 AD를 글자 그대로 지키면서도 서로 병합 불가능한 산출물을 만들 수 있다. 특히 AD-4와 AD-2는 PRD가 이미 명시적으로 요구한 규칙(페이지ID 변경 시 깨진링크 처리, 소급 변경 금지)을 스파인이 놓치고 있어, "스파인을 따랐다"는 사실 자체가 PRD 위반을 막아주지 못하는 상태다. 전체적으로 critical 3건, high 1건, medium 2건.

### Findings

- **critical** AD-5 필드 소스 플래그 — 벌크수정 경로와 단일 인라인수정 경로가 다른 규약으로 `*_source`를 갱신할 수 있음 — AD-5는 "필드 그룹마다 `*_source` 플래그를 둔다"와 "AD-5의 Application Service만 갱신한다"고만 말하는데, 화면 데이터를 건드리는 경로가 실제로는 최소 두 개다: (1) 화면 상세 패널에서 필드 하나씩 고치는 인라인 수정, (2) 엑셀 유사 그리드/리스트 뷰에서 여러 화면을 한 번에 저장하는 벌크 수정(FR-9~13이 "화면에서 직접 수정 가능"이라고만 하고 두 경로를 구분하지 않음). 빌더 A는 인라인 경로를 PATCH로 구현해 "요청 바디에 실제로 값이 바뀐 필드만 포함 → 그 필드 그룹의 `*_source`만 `manual`로 전환"하는 diff-기반 규약을 만든다. 빌더 B는 그리드 저장을 "행 전체를 하나의 폼으로 제출"하는 방식으로 구현해, 사용자가 실제로 건드리지 않은 필드까지 페이로드에 포함되므로 "페이로드에 포함된 필드 그룹은 모두 `manual`로 전환"하는 규약을 만든다. 두 구현 모두 AD-5의 문언(“필드 그룹마다 플래그를 둔다”, “Application Service만 갱신한다")을 어기지 않지만, 결과는 완전히 다르다 — 사용자가 그리드에서 페이지명만 고쳤는데 기능정의/일정까지 `manual`로 뒤바뀌어 FR-8 재실행 보호 대상이 잘못 늘어나거나, 반대로 벌크수정 UI로 명시적으로 고친 필드가 diff 실패(공백 문자 하나 차이 등)로 `auto`에 머물러 재실행 시 덮어써진다. NFR-2(데이터 내구성)를 직접 깨는 시나리오다. *Fix:* AD-5에 "`*_source` 전환은 반드시 '변경 전 값과 다른가'의 diff 결과로만 결정하며, 페이로드에 필드가 포함되어 있다는 사실만으로 전환하지 않는다"는 문장을 추가하고, 화면 mutation 경로가 여러 개라도 반드시 하나의 공유 `updateScreenFields()` 커맨드(Application Service 내 단일 함수)를 통과하도록 구조를 못박는다(즉, 그리드 저장/인라인 저장 UI가 각자 다른 update 함수를 호출하는 것을 금지).

- **critical** AD-4 `target_screen_id`의 참조 대상이 FK(UUID)인지 page_id 문자열인지, 그리고 "이름이 바뀐 경우"를 깨진 링크로 볼지가 스파인과 PRD 사이에서 충돌 — ERD는 `BUTTON_ACTION.target_screen_id`를 `uuid`로, AD-4는 이를 "nullable FK"로 서술해 대상 화면의 **행(PK)**을 가리키는 것처럼 보인다. 그런데 PRD FR-11은 정반대의 그림을 전제한다: "이동 대상은 같은 프로젝트 내 다른 **페이지ID**를 참조/링크"하고 "드롭다운/자동완성으로 페이지ID를 선택"하며, "**참조 대상 페이지ID가 삭제되거나 다른 값으로 변경되면** 깨진 링크로 표시"한다 — 즉 PRD는 "화면 이름(page_id)이 바뀌는 것" 자체를 깨진 링크 트리거로 명시한다. 빌더 A는 ERD를 그대로 따라 `target_screen_id`를 Screen.id(UUID) FK로 구현한다 — 이 경우 다른 화면의 page_id가 나중에 바뀌어도 FK는 여전히 같은 행을 정확히 가리키므로 `is_broken`은 계산되지 않는다(quarantine된 경우만 broken). 결과적으로 PRD FR-11이 명시한 "page_id 변경 시 깨진 링크" 요구사항이 구현에서 통째로 빠진다. 빌더 B는 PRD 문구("페이지ID를 선택", "페이지ID가 변경되면")를 문자 그대로 읽어 `target_screen_id`에 **page_id 문자열**을 저장한다 — 이 경우 이름이 바뀌면 자연스럽게 매칭 실패로 깨진 링크가 뜨지만, 이번엔 AD-4의 "FK" 표현 및 ERD의 `uuid` 타입과 정면으로 어긋나고, DB 레벨 참조 무결성(외래키 제약)이 아예 없어져 AD-4가 막으려던 문제(참조 무결성 보장 메커니즘)를 포기하게 된다. 두 팀이 이 포트/스키마를 나눠 구현하면 마이그레이션도, `is_broken` 계산 쿼리도 호환되지 않는다. *Fix:* AD-4를 "`target_screen_id`는 Screen.id(UUID) FK이며 page_id 문자열이 아니다. 단, 대상 화면의 `page_id`가 변경된 경우도 `is_broken`과 별개로 '대상 페이지ID 변경됨' 경고를 조회 시점에 파생 계산한다(예: 버튼-액션 생성/최종 확인 시점의 page_id 스냅샷을 별도 컬럼에 저장해 현재 값과 비교)"로 구체화한다. 즉 FK 무결성(행 참조)과 PRD가 요구하는 "이름 변경 알림"을 별개의 두 메커니즘으로 명시해야 한다.

- **critical** "이미 발급된 page_id는 소급 변경하지 않는다" — PRD가 두 번(FR-6 메뉴코드 변경, FR-9 디바이스방식 변경) 명시한 불변식이 AD-1~7 어디에도 없음 — AD-2는 page_id 유일성의 **스코프**(프로젝트 단위 복합 유니크)만 규정하고, 메뉴코드나 디바이스방식이 바뀔 때 기존 page_id를 어떻게 다뤄야 하는지는 다루지 않는다. AD-3은 메뉴 "삭제"에 대한 격리 규칙이라 메뉴코드 "변경"과는 무관하다. 빌더 A는 "일관성을 지킨다"는 선의로 메뉴코드 변경 시 해당 메뉴 소속 화면들의 `page_id`를 새 코드로 일괄 치환하는 UPDATE를 구현한다(find-and-replace) — 이는 PRD FR-6("이미 발급된 페이지ID는 소급 변경하지 않는다")을 정면으로 위반하며, 이미 엑셀로 내보내 AI 코딩 도구에 넘긴 page_id 참조들을 조용히 깨뜨린다. 빌더 B는 PRD를 그대로 따라 기존 값은 두고 신규 화면부터만 새 코드를 적용한다. 스파인의 AD 목록만 보고 리뷰하면 두 구현 모두 "AD 위반 없음"으로 통과된다 — AD 자체가 이 규칙을 담고 있지 않기 때문이다. *Fix:* 새 AD(예: AD-8) 또는 AD-2 확장: "menu_code, device_mode 등 page_id 구성요소가 변경되어도 기존에 발급된 `screen.page_id` 값은 소급 변경하지 않는다. 신규 코드/방식은 이후 신규 생성되는 화면에만 적용되며, 하나의 메뉴/프로젝트 내에 신·구 규칙이 혼재할 수 있음을 전제로 설계한다(일괄 치환 UPDATE 금지)."

- **high** `ScreenGenerationEngine`/`PromptGenerator` 포트의 입출력 계약이 정의되지 않아 MVP 구현과 Phase 2 요구사항이 서로 다른 시그니처를 전제로 만들어질 수 있음 — AD-1은 포트를 "인터페이스로 도메인 계층에 정의"하라고만 하지 어떤 객체가 오가는지는 스파인 어디에도 없다. `ScreenGenerationEngine`은 실제로는 Menu 하나만으로 동작할 수 없다: page_id 일련번호는 "10 단위 증가"이므로 같은 메뉴의 기존 화면 목록을 알아야 다음 번호를 이어 붙일 수 있고(FR-9), 디바이스코드는 Project 설정에서 오며(FR-9), FR-8 재실행 시 "수동 수정된 화면은 보존, 격리된 화면은 대상 제외"를 지키려면 quarantined/manual 상태를 아는 기존 Screen 목록이 필요하다. 빌더 A는 이 모든 조회를 Application Service가 미리 해서 얇은 파라미터(`generate(menu, existingScreens, deviceMode)`)로 넘기는 좁은 포트를 설계하고, 빌더 B는 어댑터가 스스로 Repository를 호출해 필요한 걸 가져오게 하는(포트 시그니처는 `generate(menuId)`뿐인) 두꺼운 어댑터를 설계한다 — 후자는 AD-1이 금지하려는 "도메인 코어가 아니라 리포지토리 접근이 어댑터 안에서 이뤄지는" 패턴과 미묘하게 엮여 Application Service 계층의 트랜잭션/인가 경계(AD-7)를 어댑터가 우회하게 만들 수 있다. `PromptGenerator`는 더 명확한 사례다: PRD가 이미 "Phase 2는 같은 메뉴의 다른 화면들과 전체 사이트 컨셉까지 반영한다"고 로드맵으로 못박아 놨는데(FR-12), MVP 포트를 좁게 `generatePrompt(screen, menu): string`으로 설계하면 Phase 2에서 필요한 "형제 화면 목록"과 "Project.concept"을 받을 방법이 없어 포트 시그니처를 깨는 변경이 강제된다 — AD-1이 지키려는 "통째로 교체 가능"이라는 목적 자체가 무산된다. *Fix:* AD-1에 두 포트의 최소 계약을 명시한다. 예: `ScreenGenerationEngine.generate(input: { project: Pick<Project,'device_mode'|'concept'>, menu: Menu, existingScreens: Screen[] }): ScreenDraft[]`, `PromptGenerator.generate(input: { screen: Screen, menu: Menu, siblingScreens: Screen[], projectConcept: string }): string` 같은 최소 필드셋을 스파인에 고정하고, "어댑터는 Repository를 직접 호출하지 않는다(모든 데이터는 Application Service가 조립해 넘긴다)"를 명문화한다.

- **critical** AD-7 "공통 인가 미들웨어"가 구체 메커니즘을 지정하지 않아 두 개의 서로 합성 불가능한 인가 체계가 나올 수 있음 — Rule 문구는 "모든 Application Service는 공통 인가 미들웨어를 거쳐 ... 확인한 뒤에만 Repository를 호출한다"인데, 이것이 Next.js `middleware.ts`(라우팅/엣지 계층에서 URL 패턴으로 가로채는 방식)를 뜻하는지, 아니면 Application Service 함수를 감싸는 래퍼(`withProjectAuth(fn)` 같은 고차함수/데코레이터)를 뜻하는지 스파인이 결정하지 않았다. 빌더 A는 문자 그대로 `middleware.ts`를 구현해 `/api/projects/:id/*`, `/api/menus/:id/*` 같은 matcher로 소유권 검사를 건다 — 그런데 menu_id/screen_id 경로는 project_id를 알기 위해 먼저 DB 조인이 필요하고, App Router의 Server Action은 페이지 URL로 POST되므로 어떤 프로젝트를 다루는지 URL만으로 알 수 없어 미들웨어가 검사를 건너뛴다. 새 API 라우트가 matcher 패턴에 등록되지 않으면(흔한 실수) 조용히 인가가 빠진다 — 정확히 AD-7이 막으려던 사고다. 빌더 B는 Application Service 계층에 래퍼 함수를 만들어 각 서비스 진입점에서 명시적으로 호출한다 — Rule의 "Application Service는 ... 거쳐"라는 문언과 더 정확히 일치하고 Server Action에서도 동작하지만, 미들웨어 방식과 병행 사용 시 어느 하나가 이중 검사/누락 검사를 만들 위험이 있고, 두 팀이 각자 이 경로로 절반씩 구현하면 "라우트는 미들웨어만 믿고 서비스 내부 검사 생략" vs "서비스는 래퍼가 없으면 검사 안 함"이 뒤섞여 구멍이 생긴다. *Fix:* AD-7을 구체 메커니즘으로 못박는다: "인가는 Next.js `middleware.ts`(라우팅 계층)가 아니라 Application Service 계층의 공통 래퍼 함수/데코레이터(예: `withProjectAuth`)로 구현한다. 모든 Application Service 진입점은 이 래퍼를 통해서만 export되며, 라우트 핸들러/Server Action은 래퍼를 거치지 않은 서비스 함수를 호출할 수 없다(타입 레벨에서 강제)." Server Action을 쓸지 API Route만 쓸지도 스파인에서 확정해야 이 결정이 의미가 있다.

- **medium** 증분 재실행(FR-8) 시 "새로 생성된 화면 후보" ↔ "기존 DB 화면 행"을 매칭할 식별자가 정의되지 않음 — AD-3/AD-5는 "재실행 시 수동 수정 화면은 보존, quarantined 화면은 제외"라고만 하고, ScreenGenerationEngine이 매번 새로 뽑아내는 화면 후보 목록과 기존 화면 행을 무엇으로 매칭해 "이미 있음/신규"를 가르는지는 규정하지 않는다. 빌더 A는 예측 가능한 다음 일련번호(예: 메뉴 내 마지막 `page_id` + 10)로 매칭하는데, 사용자가 중간에 화면을 수동으로 추가/삭제해 번호 체계가 흐트러지면 오매칭이 나 이미 있는 화면을 "신규"로 중복 생성하거나 반대로 실제 신규 화면을 "이미 있음"으로 스킵할 수 있다. 빌더 B는 화면 생성 시 패턴 라이브러리가 부여하는 논리적 역할 태그(예: `list`/`detail`/`create`/`done` 같은 "화면 유형")를 별도 컬럼에 저장해 그걸로 매칭한다 — 이 경우 스키마에 AD가 언급하지 않는 컬럼이 추가되고, 빌더 A의 스키마와 마이그레이션이 호환되지 않는다. *Fix:* AD-3 또는 AD-5에 "ScreenGenerationEngine이 반환하는 각 화면 후보는 안정적 매칭 키(예: `menu_id` + 패턴이 부여한 `screen_role` 태그)를 포함해야 하며, 재실행 시 기존 화면과의 매칭은 이 키로만 수행한다. `page_id`나 일련번호 추측으로 매칭하지 않는다"를 명시한다.

- **medium** AD-6의 "방식 혼재" 경고가 FR-6(메뉴코드 신/구 혼재)과 FR-9(디바이스방식 신/구 혼재) 중 무엇을 가리키는지 불명확 — AD-6은 "깨진 링크, 범위 이탈, 일정 역전, **방식 혼재**"를 파생 경고의 예시로 들지만, PRD에는 성격이 다른 두 개의 "혼재" 경고가 따로 존재한다: FR-6은 "같은 메뉴 내 신/구 **메뉴코드** 혼재"를, FR-9는 "프로젝트 내 신/구 **디바이스 대응 방식** 혼재"를 각각 화면 목록에 경고하라고 명시한다. 빌더 A는 AD-6의 "방식 혼재"를 디바이스방식 혼재만으로 좁게 구현하고, 메뉴코드 혼재 경고는 아예 만들지 않는다(스파인에 명시된 예시가 아니므로 누락을 인지하지 못함). 빌더 B는 두 경고를 하나의 "방식 혼재" 배지로 뭉뚱그려 표시해, 사용자 입장에서 원인이 코드 문제인지 디바이스 문제인지 구분할 수 없게 만든다. *Fix:* AD-6의 예시 목록을 "메뉴코드 혼재, 디바이스방식 혼재"로 분리해 두 개의 별도 파생 경고로 명시한다.
