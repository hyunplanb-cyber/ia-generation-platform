# 검수 시나리오 작성 지침

검수 시나리오를 만드는 자리는 셋이다. 셋이 같은 물건처럼 보여야 한다.

| 어디서 | 무엇으로 | 코드 |
|---|---|---|
| 판매 AI팩의 `08_검수시나리오.xlsx` | 설계도(기능정의)에서 | `lib/export/template-verify.ts` |
| 사용자가 돌리는 사이트 검수 | 실제 URL·문서를 AI가 읽고 | `adapters/verify/llm/claude-verifier.ts` |
| 앞으로 손으로 만들 것 | — | 이 문서 |

> 이 문서를 고치면 위 두 코드도 같이 맞춰야 한다. 어긋나면 산 사람이 먼저 알아챈다.

---

## 1. 왜 이 지침이 생겼나

판매팩의 검수 시나리오에 이런 줄이 실려 나갔다(2026-08-03에 발견).

```
확인 항목: 상단 히어로(카피 + 지역
확인 항목: 시술 통합 검색바)
확인 항목: 왁싱
확인 항목: 염색
```

원인은 둘이었다.

1. **자르면 안 되는 곳에서 잘랐다.** 괄호 안의 가운뎃점은 항목을 나누는 구분자가 아니라 "이런 것들이 들어간다"는 나열이다. 기능정의서 쪽은 이미 고쳐 뒀는데(`splitFuncDef`), 검수 쪽은 자기 나름의 방식으로 자르고 있었다. **같은 일을 하는 코드를 두 벌 두면 반드시 갈라진다.**
2. **'확인 방법'이 앞 칸을 베끼기만 했다.** 92줄 모두 `'X' 화면에서 {항목} — 의도대로 동작하는지 눌러 확인한다.` 였다. 줄은 채웠지만 알려주는 게 없었다.

디럭스·프리미엄에만 들어가는, 값을 5만원 넘게 올려받는 근거인 파일이다. 여기가 허술하면 나머지도 그렇게 보인다.

---

## 2. 지켜야 할 것

### 원칙 1 — 확인 항목은 "한 사람이 한 번에 확인할 수 있는 한 가지"다

너무 잘게 쪼개면 `왁싱` 같은 낱말이 남고, 안 쪼개면 한 줄에 다섯 가지가 뭉친다.

- 자르는 구분자: `·` `,` 줄바꿈
- **괄호·대괄호·중괄호 안은 자르지 않는다.** 그 안은 열거지 목록이 아니다.
- 판단이 서지 않으면 **덜 자른다.** 뭉친 항목은 읽을 수 있지만 잘린 항목은 뜻을 잃는다.

```
O  시술 카테고리 바로가기 8종(헤어컷·펌·염색·네일·왁싱·피부관리·속눈썹·두피케어)
X  시술 카테고리 바로가기 8종(헤어컷   /   펌   /   염색   /   왁싱
```

구현은 `splitFuncDef`(`lib/export/requirements.ts`) 하나만 쓴다. 새로 만들지 않는다.

### 원칙 2 — '확인 방법'은 손이 움직일 수 있게 쓴다

항목을 되풀이하지 말고, **무엇을 눌러 무엇을 보는지**를 쓴다. 항목의 성격에 따라 확인법이 다르다.

| 항목 성격 | 확인 방법은 이렇게 |
|---|---|
| 개수가 적힌 것 (`카드 4개`, `후기 3건`) | 세어 본다 — 적힌 수만큼 나오는지 |
| 입력·폼 | **빈 값**과 **잘못된 값**을 넣어 본다 |
| 버튼·링크·바로가기 | 눌러서 설계한 화면으로 가는지, 뒤로 돌아오는지 |
| 목록·필터·정렬·검색 | 조건을 바꿔 결과가 실제로 바뀌는지 |
| 예외·상태 화면 | **일부러 그 상황을 만든다** (없는 검색어, 빈 목록) |
| 결제·로그인·개인정보 | 성공·실패·취소를 **각각** 끝까지 해 본다 |
| 표시·정보 | 화면의 값이 실제 데이터와 같은지 대조한다 |

### 원칙 3 — '기대 결과'를 함께 적는다

확인만 시키고 무엇이 맞는지 안 알려주면 판정할 수 없다. **본 사람이 PASS/FAIL을 고를 수 있어야** 점검표다.

```
확인 항목   대표 콘텐츠 4개 카드
확인 방법   홈 화면을 열고 카드가 4개 다 나오는지 세어 본다.
기대 결과   4개가 빠짐없이 보이고, 깨진 이미지나 빈 칸이 없다.
```

### 원칙 3-2 — 화면별 항목만으로는 모자란다

확인 항목은 **화면별 기능정의**에서 뽑는다. 그런데 기능정의에는 뒤로가기·헤더처럼 **모든 화면이 공유하는 것**이 안 적혀 있다. 그래서 만들어진 사이트에서 화면 136개 중 105개에 뒤로가기가 없었는데도, 검수표에는 그걸 볼 칸이 없었다(2026-08-04).

표 맨 앞에 **공통 점검(`SCN-000`)**을 둔다. 사이트 전체를 두고 한 번씩만 보는 것들이다.

- 뒤로가기 · 현재 위치 · 여러 단계의 이전 단계
- 막다른 화면의 다음 행동 · 전체 화면 목록으로 가는 길
- 손님/운영자 헤더 분리 · 눌러도 반응 없는 버튼
- 이미지 자리 비율 · 공통 요소 일관성 · 모바일 가로 스크롤

> **공통 점검은 빌드 가이드(스펙팩 6장)와 짝이다.**
> 가이드에 규칙을 더하면 여기에도 확인 항목을 더한다 — **시킨 것과 보는 것이 같아야 한다.**
> 한쪽만 고치면, 지시는 했는데 확인할 칸이 없거나 그 반대가 된다.

맨 앞에 두는 이유는 순서 때문이다. 화면 백 개를 다 보고 난 뒤에 하라고 하면 이미 지쳐서 안 한다.

### 원칙 4 — 예외 상황을 반드시 넣는다

AI에게 "만들어줘" 한 줄로 시키면 **가장 확실히 빠지는 것**이 예외 화면이다. 우리 값어치가 여기 있다.

- 목록이 비었을 때
- 검색 결과가 없을 때
- 결제·전송이 실패했을 때
- 기간이 지났거나 마감됐을 때
- 권한이 없어 못 볼 때

### 원칙 5 — 개발자가 아닌 사람이 읽는다

산 사람은 대개 1인 창업자이거나 기획자다.

- `유효성 검증` → **빈 값으로 넣어 본다**
- `리다이렉트` → **다른 화면으로 넘어간다**
- `엣지 케이스` → **잘 안 생기는 상황**

겁주지 않는다. 담백하게 쓴다.

## 3. 표의 생김새

| 열 | 내용 |
|---|---|
| 테스트ID | `SCN-001` — 화면 하나에 하나. 같은 화면의 여러 항목은 ID를 공유한다 |
| 메뉴 · 화면 · 화면ID | 화면의 첫 줄에만 적는다(읽을 때 덩어리로 보이라고) |
| 화면구분 | `기본` 또는 `예외·상태` |
| 확인 항목 | 원칙 1 |
| 확인 방법 | 원칙 2 |
| 기대 결과 | 원칙 3 |
| 결과 | 비워 둔다 — 사는 사람이 PASS/FAIL/WARN을 채운다 |
| 비고 | 비워 둔다 |

**시나리오 수 = 화면 수**를 지킨다. 판매 페이지에 적히는 숫자가 이 값이라, 어긋나면 표기와 파일이 달라진다.
확인 항목이 하나도 없는 화면도 한 줄은 남긴다(`화면이 정상적으로 열리는지 확인`).

---

## 4. 숫자를 두 번 세지 않기

판매 페이지의 `검수 시나리오 N개 · 확인 항목 M개`는 **파일을 만드는 것과 같은 계산**이어야 한다.

- 세는 곳: `lib/packages.ts`의 `verifyOf()`
- 만드는 곳: `lib/export/template-verify.ts`

둘 다 `splitFuncDef`를 쓴다. 한쪽만 고치면 "368개라더니 300개네"가 된다.
